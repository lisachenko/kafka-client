# Kafka 0.8.2.2 wire protocol

This document is the grammar that the `0.8.x` branch implements. It describes **only** what Apache Kafka 0.8.2.2
speaks — the last release of the 0.8 line — so that later protocol lines (`0.9.x`, `0.10.x`, `main`) can be built by
cascade-merging this branch upwards.

Sources, in decreasing order of authority:

1. The broker itself (Apache Kafka 0.8.2.2, `docker/kafka-0.8.2.2`).
2. The 0.8.2.2 sources: `core/src/main/scala/kafka/api/*.scala`, `core/src/main/scala/kafka/message/*.scala`,
   `core/src/main/scala/kafka/common/ErrorMapping.scala`, `core/src/main/scala/kafka/api/RequestKeys.scala`
   (tag [`0.8.2.2`](https://github.com/apache/kafka/tree/0.8.2.2)).
3. The wiki page [A Guide To The Kafka Protocol](https://cwiki.apache.org/confluence/display/KAFKA/A+Guide+To+The+Kafka+Protocol).
   The wiki documents every version up to 0.10; anything marked there as "supported in 0.9.0 or later" does **not**
   exist on this branch.

Notation follows the wiki: productions are camel case, primitive types lower case, `[foo]` is an array of `foo`,
and a sequence of productions means concatenation.

## Protocol primitive types

| Type    | Encoding                                                                         |
|---------|----------------------------------------------------------------------------------|
| `int8`  | 1 byte, signed                                                                    |
| `int16` | 2 bytes, signed, big endian                                                       |
| `int32` | 4 bytes, signed, big endian                                                       |
| `int64` | 8 bytes, signed, big endian (two's complement)                                    |
| `string`| `int16` length `N` followed by `N` bytes of UTF-8; `N = -1` (`ff ff`) means `null` |
| `bytes` | `int32` length `N` followed by `N` bytes; `N = -1` (`ff ff ff ff`) means `null`    |
| `[foo]` | `int32` element count `N` followed by `N` repetitions of `foo`                     |

Byte-exact examples, as implemented by `Protocol\Kafka\IO\Stream`:

| Value                     | Bytes                     |
|---------------------------|---------------------------|
| `int16` `-1`              | `ff ff`                   |
| `int16` `-32768`          | `80 00`                   |
| `int32` `-1`              | `ff ff ff ff`             |
| `int64` `-1`              | `ff ff ff ff ff ff ff ff` |
| `string` `null`           | `ff ff`                   |
| `string` `""`             | `00 00`                   |
| `string` `"test"`         | `00 04 74 65 73 74`       |
| `bytes` `null`            | `ff ff ff ff`             |
| `bytes` `""`              | `00 00 00 00`             |
| empty array               | `00 00 00 00`             |

An empty string and a null string are different values on the wire; the client id of a request, for example, is always
an empty string and never null.

## Common request and response structure

Every request and every response is framed by its size:

```
RequestOrResponse => Size (RequestMessage | ResponseMessage)
  Size => int32
```

`Size` is the length in bytes of everything that follows it. A client reads a response by first reading these four
bytes as an integer `N` and then reading exactly `N` more bytes.

### Requests

```
RequestMessage => ApiKey ApiVersion CorrelationId ClientId RequestBody
  ApiKey        => int16
  ApiVersion    => int16
  CorrelationId => int32
  ClientId      => string
```

* `ApiKey` — numeric id of the API being invoked (see the table below).
* `ApiVersion` — version of that API; the broker answers in exactly the format that matches the requested version.
* `CorrelationId` — user-supplied value that the broker passes back unmodified.
* `ClientId` — user-supplied identifier of the client application.

A Metadata request v0 with client id `test`, correlation id `1` and an empty topic list is therefore:

```
00 00 00 12   Size = 18
00 03         ApiKey = 3 (Metadata)
00 00         ApiVersion = 0
00 00 00 01   CorrelationId = 1
00 04 74 65 73 74   ClientId = "test"
00 00 00 00   [TopicName] = empty
```

### Responses

```
Response => Size CorrelationId ResponseBody
  Size          => int32
  CorrelationId => int32
```

The broker guarantees that responses on a single connection come back in the order the requests were sent, and every
response repeats the correlation id of its request.

There is exactly one exception to the request/response symmetry: a Produce request with `RequiredAcks = 0` gets no
response at all.

## API keys

From `kafka/api/RequestKeys.scala` @ 0.8.2.2. Only version 0 of each API exists in 0.8.2.2, except for
OffsetCommit and OffsetFetch, which also have a version 1.

| ApiKey | Name (0.8.2 naming)                | Versions | Client-facing | Implemented here |
|--------|------------------------------------|----------|---------------|------------------|
| 0      | Produce (`ProducerRequest`)        | v0       | yes           | yes              |
| 1      | Fetch                              | v0       | yes           | yes              |
| 2      | Offsets (`OffsetRequest`)          | v0       | yes           | yes              |
| 3      | Metadata (`TopicMetadataRequest`)  | v0       | yes           | yes              |
| 4      | LeaderAndIsr                       | v0       | broker→broker | no               |
| 5      | StopReplica                        | v0       | broker→broker | no               |
| 6      | UpdateMetadata                     | v0       | broker→broker | no               |
| 7      | ControlledShutdown                 | v0       | controller    | no               |
| 8      | OffsetCommit                       | v0, v1   | yes           | yes              |
| 9      | OffsetFetch                        | v0, v1   | yes           | yes              |
| 10     | ConsumerMetadata                   | v0       | yes           | yes              |
| 11     | JoinGroup                          | —        | no            | no               |
| 12     | Heartbeat                          | —        | no            | no               |

ApiKeys 11 and 12 are parsed by the 0.8.2.2 broker but not handled by `KafkaApis` (the broker answers
`Unknown api code`). Everything from 13 upwards (SyncGroup, LeaveGroup, DescribeGroups, ListGroups, SaslHandshake,
ApiVersions) does not exist in 0.8.x at all — the broker closes the socket. Consumer group *membership* in 0.8 is
managed through ZooKeeper, not through the broker.

There is no SSL and no SASL in 0.8.x.

## MessageSet and Message

The message set format is shared by the Produce and Fetch APIs and by the on-disk log. Note that a `MessageSet` is
**not** preceded by an `int32` element count like a regular array — it is a raw byte region whose length is given by
the surrounding `MessageSetSize` field.

```
MessageSet => [Offset MessageSize Message]
  Offset      => int64
  MessageSize => int32

Message => Crc MagicByte Attributes Key Value
  Crc        => int32
  MagicByte  => int8
  Attributes => int8
  Key        => bytes
  Value      => bytes
```

0.8.2.2 only knows **message format v0**: `MagicByte` is `0` and there is no `Timestamp` field (that arrived with
message format v1 in 0.10.0).

* `Crc` — CRC-32 (IEEE, the same polynomial as `crc32()` in PHP) of the message bytes that follow the CRC field,
  i.e. of `MagicByte Attributes Key Value`.
* `Attributes` — the three lowest bits hold the compression codec, all other bits are 0 in 0.8.2.2:

  | Codec  | Value | Supported by this client |
  |--------|-------|--------------------------|
  | none   | 0     | yes                      |
  | gzip   | 1     | yes                      |
  | snappy | 2     | yes                      |
  | lz4    | 3     | no                       |

  (`kafka/message/CompressionCodec.scala` @ 0.8.2.2. The broker already knows the LZ4 codec, added in 0.8.2 for the
  new Java producer, but this client does not produce or consume it.)
* A compressed message is a regular message whose `Value` is a complete, compressed `MessageSet`.
* The server is allowed to return a **partial message at the end of a message set**; clients must silently drop a
  trailing message that is shorter than its announced size.
* `Offset` is the log sequence number. A producer may put anything there for uncompressed messages; for a compressed
  message set the inner offsets should start at 0 and increase by one.

## Metadata API (key 3, v0)

```
TopicMetadataRequest => [TopicName]
  TopicName => string
```

An empty topic array asks for metadata about every topic. If `auto.create.topics.enable` is set on the broker, asking
for an unknown topic creates it.

```
MetadataResponse => [Broker][TopicMetadata]
  Broker => NodeId Host Port
    NodeId => int32
    Host   => string
    Port   => int32
  TopicMetadata => TopicErrorCode TopicName [PartitionMetadata]
    TopicErrorCode => int16
    TopicName      => string
  PartitionMetadata => PartitionErrorCode PartitionId Leader Replicas Isr
    PartitionErrorCode => int16
    PartitionId        => int32
    Leader             => int32
    Replicas           => [int32]
    Isr                => [int32]
```

`Leader` is `-1` while a leader election is in progress.

This is the only request that may be addressed to any broker of the cluster.

## Produce API (key 0, v0)

```
ProduceRequest => RequiredAcks Timeout [TopicName [Partition MessageSetSize MessageSet]]
  RequiredAcks   => int16
  Timeout        => int32
  TopicName      => string
  Partition      => int32
  MessageSetSize => int32
```

```
ProduceResponse => [TopicName [Partition ErrorCode Offset]]
  TopicName => string
  Partition => int32
  ErrorCode => int16
  Offset    => int64
```

`RequiredAcks`: `0` — do not wait and **send no response at all**; `1` — wait for the leader's local log; `-1` — wait
for all in-sync replicas. `ThrottleTime` was added to the response in v1 (Kafka 0.9) and does not exist here.

## Fetch API (key 1, v0)

```
FetchRequest => ReplicaId MaxWaitTime MinBytes [TopicName [Partition FetchOffset MaxBytes]]
  ReplicaId   => int32
  MaxWaitTime => int32
  MinBytes    => int32
  TopicName   => string
  Partition   => int32
  FetchOffset => int64
  MaxBytes    => int32
```

```
FetchResponse => [TopicName [Partition ErrorCode HighwaterMarkOffset MessageSetSize MessageSet]]
  TopicName           => string
  Partition           => int32
  ErrorCode           => int16
  HighwaterMarkOffset => int64
  MessageSetSize      => int32
```

Ordinary consumers always send `ReplicaId = -1`. The response of v0 has no `ThrottleTime` prefix (that is v1, Kafka
0.9) and the returned message sets are always message format v0.

## Offsets API (key 2, v0), a.k.a. ListOffset

```
OffsetRequest => ReplicaId [TopicName [Partition Time MaxNumberOfOffsets]]
  ReplicaId          => int32
  TopicName          => string
  Partition          => int32
  Time               => int64
  MaxNumberOfOffsets => int32
```

```
OffsetResponse => [TopicName [PartitionOffsets]]
  PartitionOffsets => Partition ErrorCode [Offset]
    Partition => int32
    ErrorCode => int16
    Offset    => int64
```

`Time` is a timestamp in milliseconds with two special values: `-1` (`ff ff ff ff ff ff ff ff`) asks for the latest
offset, `-2` for the earliest available one. The timestamp-based v1 of this API arrived in 0.10.1 and does not exist
here, therefore the response has no `Timestamp` field.

## ConsumerMetadata API (key 10, v0)

Renamed to GroupCoordinator in 0.9; on this branch it keeps its 0.8.2 name.

```
ConsumerMetadataRequest => ConsumerGroup
  ConsumerGroup => string
```

```
ConsumerMetadataResponse => ErrorCode CoordinatorId CoordinatorHost CoordinatorPort
  ErrorCode       => int16
  CoordinatorId   => int32
  CoordinatorHost => string
  CoordinatorPort => int32
```

The coordinator is the broker that holds the committed offsets of the group; OffsetCommit and OffsetFetch requests
have to be sent to it.

## OffsetCommit API (key 8, v0 and v1)

Version 0 stores the offsets in ZooKeeper, version 1 stores them in the `__consumer_offsets` topic of the broker
(`kafka/api/OffsetCommitRequest.scala` @ 0.8.2.2 asserts that the version is either 0 or 1).

```
OffsetCommitRequest v0 => ConsumerGroupId [TopicName [Partition Offset Metadata]]
  ConsumerGroupId => string
  TopicName       => string
  Partition       => int32
  Offset          => int64
  Metadata        => string
```

```
OffsetCommitRequest v1 => ConsumerGroupId ConsumerGroupGenerationId ConsumerId
                          [TopicName [Partition Offset TimeStamp Metadata]]
  ConsumerGroupId           => string
  ConsumerGroupGenerationId => int32
  ConsumerId                => string
  TopicName                 => string
  Partition                 => int32
  Offset                    => int64
  TimeStamp                 => int64
  Metadata                  => string
```

```
OffsetCommitResponse v0 and v1 => [TopicName [Partition ErrorCode]]
  TopicName => string
  Partition => int32
  ErrorCode => int16
```

A client that is not a member of a group commits with generation id `-1` and an empty (not null) consumer id. If the
`TimeStamp` of v1 is left at `-1`, the broker uses its receive time. The v2 request with a global `RetentionTime`
field belongs to Kafka 0.9 and does not exist here.

## OffsetFetch API (key 9, v0 and v1)

v0 and v1 are identical on the wire; v0 reads the offsets from ZooKeeper, v1 reads them from Kafka.

```
OffsetFetchRequest => ConsumerGroup [TopicName [Partition]]
  ConsumerGroup => string
  TopicName     => string
  Partition     => int32
```

```
OffsetFetchResponse => [TopicName [Partition Offset Metadata ErrorCode]]
  TopicName => string
  Partition => int32
  Offset    => int64
  Metadata  => string
  ErrorCode => int16
```

When no offset has been committed for a topic-partition the broker does not set an error code — it returns offset
`-1` and empty metadata.

## Error codes

From `kafka/common/ErrorMapping.scala` @ 0.8.2.2. Nothing above `20` exists in 0.8.x.

| Code | Name (0.8.2)                    | Meaning                                                        |
|------|---------------------------------|----------------------------------------------------------------|
| -1   | Unknown                         | Unexpected server error                                          |
| 0    | NoError                         | Success                                                          |
| 1    | OffsetOutOfRange                | The requested offset is outside the range kept by the server     |
| 2    | InvalidMessage                  | Message CRC does not match, the message is corrupt               |
| 3    | UnknownTopicOrPartition         | This server does not host this topic-partition                   |
| 4    | InvalidFetchSize                | The requested fetch size is invalid                              |
| 5    | LeaderNotAvailable              | No leader for the partition, a leader election is in progress    |
| 6    | NotLeaderForPartition           | This broker is not the leader for that partition                 |
| 7    | RequestTimedOut                 | The request exceeded its timeout on the broker                   |
| 8    | BrokerNotAvailable              | Broker-internal error code, should not reach a client            |
| 9    | ReplicaNotAvailable             | A requested replica is not part of the assignment any more       |
| 10   | MessageSizeTooLarge             | The message is larger than `message.max.bytes`                   |
| 11   | StaleControllerEpoch            | Controller moved to another broker                               |
| 12   | OffsetMetadataTooLarge          | The committed offset metadata exceeds the configured maximum     |
| 13   | StaleLeaderEpoch                | Reserved, never produced by 0.8.2.2                              |
| 14   | OffsetsLoadInProgress           | The coordinator is still loading the offsets of the group        |
| 15   | ConsumerCoordinatorNotAvailable | The `__consumer_offsets` topic is not available yet              |
| 16   | NotCoordinatorForConsumer       | This broker is not the coordinator of that group                 |
| 17   | InvalidTopic                    | The topic name is invalid, or is an internal topic               |
| 18   | MessageSetSizeTooLarge          | The message set exceeds the maximum accepted size                |
| 19   | NotEnoughReplicas               | Fewer in-sync replicas than `min.insync.replicas`                |
| 20   | NotEnoughReplicasAfterAppend    | The message was appended but not replicated to enough replicas   |

Note the 0.8.2 naming: what later releases call `CorruptMessage` is `InvalidMessage` here, `MessageTooLarge` is
`MessageSizeTooLarge`, and the group-related codes 14–16 speak of *consumers*, not of *groups*.
