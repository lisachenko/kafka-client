# Kafka 0.10.2.2 wire protocol

This document is the grammar that the `0.10.x` branch implements. It describes **only** what Apache Kafka 0.10.2.2
speaks — the last release of the 0.10 line, so it covers the additions of 0.10.0, 0.10.1 and 0.10.2 — so that the
line above (`main`, Kafka 0.11) can be built by cascade-merging this branch upwards. The grammar of the line below
is on `0.9.x`, in the file `docs/protocol/0.9.0.md`.

Sources, in decreasing order of authority:

1. The broker itself (Apache Kafka 0.10.2.2, `docker/kafka-0.10.2.2`).
2. The 0.10.2.2 sources: `clients/src/main/java/org/apache/kafka/common/protocol/{ApiKeys,Errors,Protocol}.java` and
   `clients/src/main/java/org/apache/kafka/common/requests/*.java`, which are the authority for every api the broker
   parses with the schemas of the Java client — that is all of them but ControlledShutdown — plus
   `core/src/main/scala/kafka/server/KafkaApis.scala`, `core/src/main/scala/kafka/network/{SocketServer,RequestChannel}.scala`,
   `core/src/main/scala/kafka/coordinator/*.scala`, `core/src/main/scala/kafka/message/*.scala` and
   `core/src/main/scala/kafka/api/ControlledShutdownRequest.scala`
   (tag [`0.10.2.2`](https://github.com/apache/kafka/tree/0.10.2.2)).
3. The wiki page [A Guide To The Kafka Protocol](https://cwiki.apache.org/confluence/display/KAFKA/A+Guide+To+The+Kafka+Protocol).
   The wiki stops at 0.10; anything it marks as "supported in 0.11 or later" does **not** exist on this branch.

Notation follows the wiki: productions are camel case, primitive types lower case, `[foo]` is an array of `foo`,
and a sequence of productions means concatenation.

Unlike the two lines below it, this branch does not have to guess what its broker speaks: Kafka 0.10.0 added the
**ApiVersions** api (key 18), and the api-key table below is the answer of a real 0.10.2.2 broker to it.

## What 0.10.2.2 adds to the 0.9.0.1 protocol

The 0.10 line raised the protocol three times, and a 0.10.2.2 broker serves all of it — as well as every version
the lines below it had.

| Area | 0.9.0.1 | 0.10.2.2 | Since |
|---|---|---|---|
| Api keys | 0-16 | 0-20: **SaslHandshake 17, ApiVersions 18** (0.10.0), **CreateTopics 19, DeleteTopics 20** (0.10.1) | 0.10.0 / 0.10.1 |
| Produce (0) | v0, v1 | v0, v1, **v2** - the response gains `LogAppendTime` int64 per partition, and the message set it carries is format v1 | 0.10.0 |
| Fetch (1) | v0, v1 | v0, v1, **v2** (identical schema; it announces that the client understands message format v1), **v3** (a top-level `MaxBytes` int32 *after* `MinBytes`, and the partition order of the request becomes significant) | 0.10.0 / 0.10.1 |
| Offsets (2) | v0 | v0, **v1** - the request partition loses `MaxNumOffsets`, the response partition becomes `Partition ErrorCode Timestamp Offset` with **one** offset | 0.10.1 |
| Metadata (3) | v0 | v0, **v1** (the request topic array becomes **nullable**, the response gains `ControllerId` and a broker `Rack`, every topic an `IsInternal` boolean), **v2** (a `ClusterId` nullable string before `ControllerId`) | 0.10.0 / 0.10.1 |
| ControlledShutdown (7) | v0, v1 | **v1 only** as far as ApiVersions is concerned; the frame of v0 is still parsed, see the api-key table | 0.10.0 |
| OffsetFetch (9) | v0, v1 | v0, v1, **v2** - the topic array becomes **nullable** (`null` = every topic of the group) and the response gains a top-level `ErrorCode` int16 *after* the topics | 0.10.2 |
| JoinGroup (11) | v0 | v0, **v1** - the request gains `RebalanceTimeout` int32 after `SessionTimeout`, the wire half of `max.poll.interval.ms` | 0.10.1 |
| OffsetCommit (8), GroupCoordinator (10), Heartbeat (12), LeaveGroup (13), SyncGroup (14), DescribeGroups (15), ListGroups (16) | v0-v2 / v0 … | unchanged. Their next version, which carries a `ThrottleTime`, is Kafka **0.11** | – |
| Message format | v0 | v0 and **v1**: magic byte 1, an int64 `Timestamp` between `Attributes` and `Key`, bit 3 of `Attributes` as the timestamp type, **relative** inner offsets in a compressed set, and **LZ4** (codec 3) | 0.10.0 |
| Group states | `PreparingRebalance`, `AwaitingSync`, `Stable`, `Dead` | …and **`Empty`**: a group whose last member left keeps its offsets instead of being dropped | 0.10.1 |
| Error codes | -1 … 31 | -1 … **44** | 32-35: 0.10.0, 36-42: 0.10.1, 43-44: 0.10.2 |
| Transport | PLAINTEXT, SSL | PLAINTEXT, SSL and **SASL_PLAINTEXT / SASL_SSL** with a handshake api and the **PLAIN** mechanism next to GSSAPI | 0.10.0 |
| An unparseable frame | dropped, the connection survives | the broker **closes the connection** | 0.10.0 |

Everything else in this document is the 0.9.0.1 grammar, unchanged and re-verified against a 0.10.2.2 broker.

## Implementation model

Protocol classes do not hand-roll `pack()`/`unpack()` calls: every message and DTO declares its binary layout and the
engine reads and writes it. This is the same internal design as the `main` branch, so that the cascade merges upwards
stay mechanical.

* `Protocol\Kafka\Protocol\BinarySchemaInterface::getScheme(): array` maps a property name to its type.
* `Protocol\Kafka\Protocol\BinarySchema` is the engine: `readObjectFromStream()`, `writeObjectToStream()`,
  `readSingleType()`, `writeSingleType()`, `getObjectTypeSize()`.
* A request extends its parent scheme: `parent::getScheme() + ['topics' => [BinarySchema::TYPE_STRING]]`.
* Arrays are `[ItemType]` for a plain list, `['keyField' => ItemClass::class]` for a list indexed by one of the item
  fields, and gain `BinarySchema::FLAG_NULLABLE => true` when `-1` is a valid count.

The 0.10 type set is the one of 0.9 plus one primitive: `TYPE_INT8`, `TYPE_INT16`, `TYPE_INT32`, `TYPE_INT64`,
**`TYPE_BOOLEAN`**, `TYPE_STRING`, `TYPE_NULLABLE_STRING`, `TYPE_BYTEARRAY` (nullable) and int32-prefixed arrays.
`TYPE_BOOLEAN` is what the `IsInternal` of Metadata v1 and the `ValidateOnly` of CreateTopics v1 are made of, and
0.10 is also the first line on which a *request* carries a nullable array (the topics of Metadata v1 and of
OffsetFetch v2), so `null` written as `ff ff ff ff` and `[]` written as `00 00 00 00` are two different requests
here. There are still no varints, no zigzag encoding and no var-arrays - those belong to the 0.11 record format.

An api that has more than one version and whose layout changes between them is described by one class per version:
a scheme is a static property of a class, so `OffsetCommitRequest` (the highest version) and `OffsetCommitRequestV0`
differ in their `VERSION` constant, which the version-aware `getScheme()` of the request and of its DTOs follows.

Two defects of the engine on `main` are fixed in this port: `TYPE_INT8` is read as a **signed** value (the Attributes
byte of a Message and the error codes are signed), and `TYPE_BYTEARRAY` round-trips `null` as the int32 `-1` that the
specification prescribes.

## Protocol primitive types

| Type    | Encoding                                                                         |
|---------|----------------------------------------------------------------------------------|
| `int8`  | 1 byte, signed                                                                    |
| `int16` | 2 bytes, signed, big endian                                                       |
| `int32` | 4 bytes, signed, big endian                                                       |
| `int64` | 8 bytes, signed, big endian (two's complement)                                    |
| `boolean` | 1 byte: `00` is false, **any** non-zero byte is true; this client writes `01`   |
| `string`| `int16` length `N` followed by `N` bytes of UTF-8; `N = -1` (`ff ff`) means `null` |
| `bytes` | `int32` length `N` followed by `N` bytes; `N = -1` (`ff ff ff ff`) means `null`    |
| `[foo]` | `int32` element count `N` followed by `N` repetitions of `foo`                     |

Byte-exact examples, as implemented by `Protocol\Kafka\IO\Stream`:

| Value                     | Bytes                     |
|---------------------------|---------------------------|
| `int16` `-1`              | `ff ff`                   |
| `int16` `-32768`          | `80 00`                   |
| `int32` `-1`              | `ff ff ff ff`             |
| `int64` `-1`              | `ff ff ff ff ff ff ff ff` |
| `string` `null`           | `ff ff`                   |
| `string` `""`             | `00 00`                   |
| `string` `"test"`         | `00 04 74 65 73 74`       |
| `bytes` `null`            | `ff ff ff ff`             |
| `bytes` `""`              | `00 00 00 00`             |
| `boolean` `false` / `true`| `00` / `01`               |
| empty array               | `00 00 00 00`             |
| null array                | `ff ff ff ff`             |

An empty string and a null string are different values on the wire; the client id of a request, for example, is always
an empty string and never null.

## Common request and response structure

Every request and every response is framed by its size:

```
RequestOrResponse => Size (RequestMessage | ResponseMessage)
  Size => int32
```

`Size` is the length in bytes of everything that follows it. A client reads a response by first reading these four
bytes as an integer `N` and then reading exactly `N` more bytes.

### Requests

```
RequestMessage => ApiKey ApiVersion CorrelationId ClientId RequestBody
  ApiKey        => int16
  ApiVersion    => int16
  CorrelationId => int32
  ClientId      => string
```

* `ApiKey` — numeric id of the API being invoked (see the table below).
* `ApiVersion` — version of that API; the broker answers in exactly the format that matches the requested version.
* `CorrelationId` — user-supplied value that the broker passes back unmodified.
* `ClientId` — user-supplied identifier of the client application.

A Metadata request v0 with client id `test`, correlation id `1` and an empty topic list is therefore:

```
00 00 00 12   Size = 18
00 03         ApiKey = 3 (Metadata)
00 00         ApiVersion = 0
00 00 00 01   CorrelationId = 1
00 04 74 65 73 74   ClientId = "test"
00 00 00 00   [TopicName] = empty
```

### Responses

```
Response => Size CorrelationId ResponseBody
  Size          => int32
  CorrelationId => int32
```

The broker guarantees that responses on a single connection come back in the order the requests were sent, and every
response repeats the correlation id of its request.

There is exactly one exception to the request/response symmetry: a Produce request with `RequiredAcks = 0` gets no
response at all.

### An api the broker does not serve closes the connection

**This is the behaviour that changed in Kafka 0.10, and it is the one a client of a lower line gets wrong.** A
0.9.0.1 broker silently *dropped* a frame it could not parse and kept the connection open; a 0.10.2.2 broker
**closes the connection**.

`RequestChannel.Request` @ 0.10.2.2 parses every incoming frame with
`AbstractRequest.getRequest(apiKey, apiVersion, buffer)` and wraps whatever that throws — an unknown api key, a
version outside `Protocol.CURR_VERSION`, or a body that does not match the schema of the version it claims — into an
`InvalidRequestException`. `SocketServer.processCompletedReceives` catches that and the `SchemaException` of the
schema layer and closes the channel:

```
ERROR Closing socket for 172.18.0.2:9092-172.18.0.1:43460 because of error (kafka.network.Processor)
org.apache.kafka.common.errors.InvalidRequestException: Error getting request for apiKey: 8 and apiVersion: 3
```

```
ERROR Closing socket for 172.18.0.2:9092-172.18.0.1:43482 because of error (kafka.network.Processor)
org.apache.kafka.common.errors.InvalidRequestException: Error getting request for apiKey: 11 and apiVersion: 1
Caused by: org.apache.kafka.common.protocol.types.SchemaException: Error reading field 'member_id': Error reading
string of length 25455, only 10 bytes available
```

The second example is a JoinGroup **v1** frame carrying a **v0** body: the key and the version are served, the bytes
behind them are not, and the connection is lost just the same. A malformed body is therefore as expensive as an
unknown api.

For a client this means:

* The answer to "why did my request never come back" is now "the broker hung up", not "the broker dropped it". A
  read on that connection ends in the end of the stream, which this client reports as `NetworkException` (code 13),
  not in a request timeout.
* Only that one connection is lost. The broker itself is unaffected, and the next connection is answered normally.
* A client must never send a version it has not seen in an ApiVersions answer. This branch therefore hard-codes the
  versions of 0.10.2.2 and `ApiKeys` stops at 20.

There are exactly **two** exceptions, and both are verified by the probe:

**ApiVersions answers an unknown version instead of closing.** `RequestChannel.Request` special-cases key 18: for a
version `Protocol.apiVersionSupported()` rejects it builds a dummy request, so that
`KafkaApis.handleApiVersionsRequest` can answer `ApiVersionsResponse.fromError(UNSUPPORTED_VERSION)` — the error
code **35** with an empty api array, written in the layout of **version 0** no matter which version was asked for.
The connection survives, which is what makes the answer usable: a client that guessed too high reads the 35 and
retries with version 0. This is the whole reason the api can be the first request on a connection.

**ControlledShutdown answers every version**, see below.

### The last Scala api does not check its version

Kafka 0.10 moved every api but one to the schemas of the Java client, which validate the version. The exception is
**ControlledShutdown (key 7)**: `RequestChannel.Request` calls `ControlledShutdownRequest.readFrom(buffer)` for that
key before the request header is parsed at all — the source carries the comment *"this will be removed once we
remove support for v0 of ControlledShutdownRequest (which depends on a non-standard request header)"* — and that
parser only asks whether the version is above 0, to decide whether a client id follows:

```scala
val versionId     = buffer.getShort
val correlationId = buffer.getInt
val clientId      = if (versionId > 0) Some(readShortString(buffer)) else None
val brokerId      = buffer.getInt
```

A 0.10.2.2 broker therefore answers key 7 with **any** version — the retired v0 without a client id, the v1 of the
table, and v2 or above like v1 — although ApiVersions reports the single version 1 for it. Nothing may be read into
that: only version 1 is the protocol of 0.10.2.2, the rest is an accident of the last Scala parser, and this client
sends v1. The v0 class is kept for the `0.8.x`/`0.9.x` vectors.

The keys 0 to 6 and 8 to 9, which the 0.9 line still described as "Scala apis that do not check their version", have
all lost that property: a 0.10.2.2 broker closes the connection for Produce v3, Fetch v4, Offsets v2, Metadata v3,
UpdateMetadata v4, OffsetCommit v3 and OffsetFetch v3 alike.

### What is not in Kafka 0.10.2.2

Everything below is Kafka **0.11** and must not appear on this branch:

* **Record batches v2** — magic byte 2, the batch header with a producer id, an epoch and a sequence number, varint
  and zigzag encoding, headers per record, and the delta encoding of offsets and timestamps inside a batch. The
  message format of this line is v0 and v1, one `Message` per entry with a CRC of its own.
* **Idempotent and transactional producers**, and the api keys they need: `InitProducerId` (22),
  `AddPartitionsToTxn` (24), `AddOffsetsToTxn` (25), `EndTxn` (26), `WriteTxnMarkers` (27), `TxnOffsetCommit` (28).
  Also `DeleteRecords` (21), `OffsetForLeaderEpoch` (23), `DescribeAcls` (29), `CreateAcls` (30), `DeleteAcls` (31)
  and `DescribeConfigs` / `AlterConfigs` (32, 33). `ApiKeys` stops at **20** here.
* **`ThrottleTimeMs` in the group apis.** OffsetCommit v3, GroupCoordinator v1, JoinGroup v2, Heartbeat v1,
  LeaveGroup v1, SyncGroup v1, DescribeGroups v1 and ListGroups v1 add it, and all of them are 0.11. The throttle
  time of this line exists only in Produce v1 and above and Fetch v1 and above.
* **Metadata v3/v4**, **Produce v3**, **Fetch v4/v5**, **Offsets v2**, **OffsetFetch v3**, **CreateTopics v2** — the
  0.11 versions of the apis this line has.
* **`isolation_level`** and the read-committed consumer, **`log_start_offset`**, and the `SaslAuthenticate` api
  (key 36, Kafka 1.0): the SASL token exchange of this line is raw, unframed data on the socket after the handshake.
* **Error codes above 44.**

## ApiVersions API (key 18, v0)

Asks a broker which api keys and versions it serves. Kafka 0.10.0 added it, and it is the only request whose answer
tells a client what the peer on the other side speaks; on the two lines below this one there is no such api, and
the api-key table had to be probed frame by frame.

```
ApiVersionsRequest =>
```

The request has **no body at all** — only the common request header — so the whole frame is 4 bytes of `Size` plus
8 bytes of header plus the client id.

```
ApiVersionsResponse => ErrorCode [ApiKey MinVersion MaxVersion]
  ErrorCode  => int16
  ApiKey     => int16
  MinVersion => int16
  MaxVersion => int16
```

* `ErrorCode` belongs to the whole answer and is `0` or **35** (`UnsupportedVersion`).
* One entry per api the broker knows, in ascending order of `ApiKey`, including the broker-to-broker keys 4, 5 and 6
  that no client ever sends. Both version bounds are **inclusive**.
* A 0.10.2.2 broker answers with the 21 keys 0 to 20 of the api-key table above. A client must not assume that set:
  the whole point of the api is that a later broker reports more, and an older one answers nothing.

`Protocol\Kafka\Protocol\Request\ApiVersionsResponse` indexes the array by `ApiKey`, so a caller asks for one api
directly (`supports(ApiKeys::FETCH, 3)`, `maxVersionOf(ApiKeys::METADATA)`).
`Client::apiVersions(Node $node)` returns the whole response and `Admin\AdminClient::getApiVersions(Node $node)` the
indexed array; every broker answers for itself, so a rolling upgrade shows up as brokers with different ranges.

**This client does not negotiate with the answer.** Like the `0.9.x` line it sends the fixed versions a broker of
its own Kafka release serves — the "Implemented here" column of the api-key table — and the api is there to report
what the peer is, not to choose a version at runtime.

Three properties make the request usable as the *first* frame on a connection, and all three are verified against
the container:

1. **An unknown version is answered, not punished.** Every other key or version a 0.10.2.2 broker cannot parse costs
   the connection; ApiVersions is special-cased in `RequestChannel.Request`, so a version it does not serve comes
   back as the error code 35 with an **empty** api array, in the layout of **version 0**, and the connection stays
   open. A client that guessed too high therefore learns the truth instead of having to reconnect. Since version 0
   is the only version of this api in 0.10.2.2, a 35 from a real 0.10 broker can only mean that the client asked for
   a version that does not exist yet.
2. **It is answered before authentication.** On a SASL listener the broker answers ApiVersions while the connection
   is still unauthenticated (`KafkaApis.handleApiVersionsRequest` says so in a comment), so a client can learn the
   surface of a broker before it knows whether it may talk to it at all. On an SSL listener the TLS handshake still
   comes first.
3. **It is cheap.** The request carries no state, changes nothing, and the answer of a 0.10.2.2 broker is 140 bytes
   with a 23-character client id.

An older broker has no key 18: a **0.9.0.1** broker drops the frame and never answers it, a **0.8.2.2** broker
closes the socket. "No answer at all" is therefore how a client recognises a pre-0.10 peer — there is no error code
for it.

## MessageSet and Message

The message set format is shared by the Produce and Fetch APIs and by the on-disk log. Note that a `MessageSet` is
**not** preceded by an `int32` element count like a regular array — it is a raw byte region whose length is given by
the surrounding `MessageSetSize` field.

Kafka 0.10.0 added **message format v1** (KIP-31 and KIP-32) next to the format v0 of 0.8 and 0.9. A 0.10.2.2 broker
reads and writes both, and the `MagicByte` of a message says which one it is in — it is the discriminator that has to
be read before the rest of the message:

```
MessageSet => [Offset MessageSize Message]
  Offset      => int64
  MessageSize => int32

Message (MagicByte = 0) => Crc MagicByte Attributes Key Value
  Crc        => int32
  MagicByte  => int8
  Attributes => int8
  Key        => bytes
  Value      => bytes

Message (MagicByte = 1) => Crc MagicByte Attributes Timestamp Key Value
  Crc        => int32
  MagicByte  => int8
  Attributes => int8
  Timestamp  => int64
  Key        => bytes
  Value      => bytes
```

* `Crc` — CRC-32 (IEEE, the same polynomial as `crc32()` in PHP) of the message bytes that follow the CRC field,
  i.e. of `MagicByte Attributes [Timestamp] Key Value`. The `Timestamp` of a v1 message is part of the checksum.
* `Attributes`:

  | Bits | Meaning | Values |
  |------|---------|--------|
  | 0–2  | compression codec | 0 none, 1 gzip, 2 snappy, **3 lz4** |
  | 3    | timestamp type (v1 only) | 0 `CreateTime`, 1 `LogAppendTime` |
  | 4–7  | reserved, always 0 | |

  All four codecs are implemented by this client. In a message of format v0 bit 3 is reserved and stays 0.
* `Timestamp` — milliseconds since the epoch, or **-1** (`Message.NoTimestamp`) for a message that carries none. The
  broker accepts -1 and stores it as it is; `message.timestamp.difference.max.ms` (unlimited by default) is what
  bounds a `CreateTime` that is far away from the clock of the broker, and a violation is answered with
  **32 `InvalidTimestamp`**.
* The timestamp type is a property of the **topic** (`message.timestamp.type`, `CreateTime` by default): with
  `LogAppendTime` the broker overwrites the timestamp of every message it appends with its own clock and sets bit 3
  of the attributes.
* A compressed message is a regular message whose `Value` is a complete, compressed `MessageSet`.
* The server is allowed to return a **partial message at the end of a message set**; clients must silently drop a
  trailing message that is shorter than its announced size. The size of the smallest possible message —
  `MinMessageOverhead`, 14 bytes — is the one of a format v0 message without key and value, and a `MessageSize`
  below it means a corrupt set (a format v1 message without key and value is 22 bytes).

### Offsets inside a compressed message set

The `Offset` of the entries of a *produced* set is ignored: the broker assigns the real offsets when it appends the
set, so a producer numbers its messages 0, 1, 2 … Inside a **compressed** set the two message formats differ:

* **v0** — the broker rewrites the offset of every inner message with the absolute offset of the log.
* **v1** — the inner offsets stay **relative** (0, 1, 2 …) and only the offset of the **wrapper** message is
  rewritten, with the absolute offset of the *last* inner message. A reader has to decompress the whole set to see
  the last relative offset before it can translate the others:

      absolute = wrapperOffset - lastInnerOffset + innerOffset

  (`ByteBufferMessageSet.scala` and `RecordsIterator.DeepRecordsIterator` @ 0.10.2.2). The reason is streaming
  compression: the relative offset of an inner message is known while it is written, its absolute one is not.
  The vectors `messageformat.v1.createtime.gzip` and `messageformat.v0.lz4.broken-checksum` below are the same three
  records at the offsets 3, 4 and 5 in both formats: relative `0, 1, 2` under a wrapper at offset 5 in v1, absolute
  `3, 4, 5` under the very same wrapper offset in v0.

### Timestamps inside a compressed message set

The wrapper message of a v1 set carries the timestamp of the whole batch, and it is the only message whose
attributes are meaningful:

* the timestamp type of the wrapper applies to **every** message of the set;
* with `CreateTime` the wrapper carries the **largest** timestamp of its inner messages, and every inner message
  keeps its own;
* with `LogAppendTime` the wrapper carries the append time of the batch and the timestamps of the inner messages are
  **ignored** — the broker does not even rewrite them, as `messageformat.v1.logappendtime.gzip` below shows: the
  wrapper announces `0x09` (gzip + LogAppendTime) and the append time, while the compressed inner messages still
  hold the `CreateTime` values of the producer;
* a producer must write `CreateTime` in the attributes of every inner message, otherwise the broker rejects the set.

### The lz4 codec and the KAFKA-3160 checksum

The `Value` of an lz4 message is an **LZ4 frame** (the v1.5.1 frame format), as `KafkaLZ4BlockOutputStream` writes
it: the magic number `04 22 4d 18`, the `FLG` byte `0x60` (version 1, independent blocks, no checksums), the `BD`
byte `0x40` (64 KiB blocks), the header checksum `HC`, then `int32` little-endian block lengths with their blocks,
and a block length of `0` as the end mark. The highest bit of a block length marks a block that is stored
uncompressed because compressing it made it bigger.

`HC` is the second byte of the xxHash32 of the frame descriptor, `(xxh32(FLG BD) >> 8) & 0xff` = `0x82`. Until
Kafka 0.10.0 the clients hashed the magic number **together with** the descriptor, which gives `0x1a`
([KAFKA-3160](https://issues.apache.org/jira/browse/KAFKA-3160)). The fix could not be applied to the messages that
older clients still have to read, so the broken checksum became part of the format of **message format v0** and the
correct one is used from format v1 on (`MemoryRecordsBuilder.wrapForOutput()`:
`useBrokenFlagDescriptorChecksum = magic == 0`). A reader has to accept both, which is what this client does — the
0.10.2.2 broker itself writes `04 22 4d 18 60 40 1a` in every answer it down-converts to format v0.

### What the broker converts, and when

The message format of the **log** is the `message.format.version` of the topic (`log.message.format.version` of the
broker by default, `0.10.2` on the container of this branch), and the broker converts whatever it is given:

| Producer writes | Topic format | Stored as | Fetch v0/v1 answers | Fetch v2 answers |
|---|---|---|---|---|
| v1 | 0.10.x | v1, timestamps kept | **v0**, no timestamps, absolute inner offsets | v1, as stored |
| v0 | 0.10.x | **v1**, `Timestamp` = -1 (`NoTimestamp`) | v0 | v1 with -1 timestamps |
| v1 | 0.9.0 | **v0**, timestamps dropped | v0 | v0 |
| v0 | 0.9.0 | v0 | v0 | v0 |

The down-conversion of the answer is what `KafkaApis.handleFetchRequest` does for a client that asks with a Fetch
request below **version 2**: `versionId <= 1 && getMagic(tp) > 0` ⇒ `records.toMessageFormat(MAGIC_VALUE_V0)`. It
strips the timestamps, turns the relative inner offsets into absolute ones and recompresses the set with the same
codec — with the broken lz4 checksum, since the result is a format v0 set. Version 2 of the Fetch API is *only* the
statement "I understand message format v1"; its request and its response are byte-identical to version 1.

A client of this branch therefore sees timestamps only through a Fetch v2 request, which the Fetch ticket of this
line adds; `Record::$timestamp` is `null` and `Record::$timestampType` is `NO_TIMESTAMP_TYPE` for everything that
arrives in format v0.

## Produce API (key 0, v0 and v1)

A 0.9.0.1 broker does not reject a higher version of this request either — `ProducerRequest.readFrom` has no version
assertion and treats everything above 0 as v1 — but only 0 and 1 are the versions of the release, and this client
sends nothing else.

## Quotas and throttle time

Kafka 0.9 introduced client quotas (KIP-13), and the `ThrottleTime` of Produce v1 and the `ThrottleTimeMs` of Fetch
v1 are the only place where a client sees them. A quota is a byte rate per `client.id`, stored in ZooKeeper under
`/config/clients/<client id>` and changed on a running broker with

```console
$ kafka-configs.sh --zookeeper localhost:2181 --alter \
    --add-config 'producer_byte_rate=1024,consumer_byte_rate=1024' \
    --entity-type clients --entity-name my-application
$ kafka-configs.sh --zookeeper localhost:2181 --alter \
    --delete-config producer_byte_rate,consumer_byte_rate \
    --entity-type clients --entity-name my-application
```

The broker watches that path and applies the change within milliseconds, no restart is needed
(`kafka/server/ConfigHandler.scala` @ 0.9.0.1, where the two keys are `producer_byte_rate` and `consumer_byte_rate`).
Without an override the broker defaults `quota.producer.default` and `quota.consumer.default` apply, and those are
`Long.MaxValue`, i.e. unlimited — which is why every vector captured on the test broker carries a throttle time of
zero.

**A quota never rejects anything.** There is no error code for it in 0.9: the broker appends the records, or reads
them, and then *delays the answer*. `ClientQuotaManager.recordAndMaybeThrottle` records the size of the request
against a rate over `quota.window.num` samples of `quota.window.size.seconds` each — 11 samples of one second by
default, so the rate is measured over a window of about ten seconds — and when that rate exceeds the bound it puts
the response into a delay queue for

```
throttleTimeMs = (observedRate - quotaBound) / quotaBound * windowSizeMs
```

milliseconds before it is written to the socket (`kafka/server/ClientQuotaManager.scala` @ 0.9.0.1). The answer then
carries that very number, so a client that measures the round trip of a throttled request finds the same value
again; the field is informational, the waiting has already happened by the time it is read.

What is counted differs between the two apis (`KafkaApis.handleProducerRequest` and `KafkaApis.handleFetchRequest`
@ 0.9.0.1):

* **Produce** records `produceRequest.sizeInBytes`, the size of the whole request frame the client sent.
* **Fetch** records the size of the *response*, and never throttles a fetch of a replica
  (`fetchRequest.isFromFollower`), so replication traffic is unaffected by consumer quotas.

A fire-and-forget batch (`RequiredAcks = 0`) is throttled as well, and the client never learns about it: the
throttle callback of the broker runs after the delay and then does nothing, because such a request has no response.
This is why `RecordMetadata::$throttleTimeMs` is 0 for `acks = 0` — like the offset of such a batch, it is
simply unknown.

Observed on the broker of `docker/kafka-0.9.0.1` with `producer_byte_rate=1024` and a client id of its own: ten
produce requests of 1113 bytes each were acknowledged without a delay, and the tenth answer came back after 793 ms
with `ThrottleTime = 793`. With `consumer_byte_rate=1024`, the second fetch of 8242 bytes was delayed by 6089 ms and
answered with `ThrottleTimeMs = 6089`; a following fetch at the high watermark, which returned no records at all,
still waited 5943 ms, because the rate of the window is what is over the bound, not the single request. Both
answers are the vectors `produce.response.v1.throttled` and `fetch.response.v1.throttled` below.

## GroupCoordinator API (key 10, v0)

Called `ConsumerMetadataRequest` in the 0.8.2 sources; the client uses the `main` name, `GroupCoordinatorRequest`.

```
GroupCoordinatorRequest => ConsumerGroup
  ConsumerGroup => string
```

```
GroupCoordinatorResponse => ErrorCode CoordinatorId CoordinatorHost CoordinatorPort
  ErrorCode       => int16
  CoordinatorId   => int32
  CoordinatorHost => string
  CoordinatorPort => int32
```

The coordinator is the broker that holds the committed offsets of the group; OffsetCommit and OffsetFetch requests

## OffsetCommit API (key 8, v0, v1 and v2)

Version 0 stores the offsets in ZooKeeper, versions 1 and 2 store them in the `__consumer_offsets` topic of the
broker. `kafka/api/OffsetCommitRequest.scala` @ 0.9.0.1 asserts that the version is 0, 1 or 2 - it is one of the two
apis that check their version at all - and a frame above that is **silently dropped**, see "An api the broker does
not serve is dropped, not refused" above: the socket stays open and the request is simply never answered. Verified
against the broker.

```
OffsetCommitRequest v0 => ConsumerGroupId [TopicName [Partition Offset Metadata]]
  ConsumerGroupId => string
  TopicName       => string
  Partition       => int32
  Offset          => int64
  Metadata        => string
```

```
OffsetCommitRequest v1 => ConsumerGroupId ConsumerGroupGenerationId ConsumerId
                          [TopicName [Partition Offset TimeStamp Metadata]]
  ConsumerGroupId           => string
  ConsumerGroupGenerationId => int32
  ConsumerId                => string
  TopicName                 => string
  Partition                 => int32
  Offset                    => int64
  TimeStamp                 => int64
  Metadata                  => string
```

```
OffsetCommitRequest v2 => ConsumerGroupId ConsumerGroupGenerationId ConsumerId RetentionTime
                          [TopicName [Partition Offset Metadata]]
  ConsumerGroupId           => string
  ConsumerGroupGenerationId => int32
  ConsumerId                => string
  RetentionTime             => int64
  TopicName                 => string
  Partition                 => int32
  Offset                    => int64
  Metadata                  => string
```

```
OffsetCommitResponse v0, v1 and v2 => [TopicName [Partition ErrorCode]]
  TopicName => string
  Partition => int32
  ErrorCode => int16
```

A client that is not a member of a group commits with generation id `-1` and an empty (not null) consumer id. If the
`TimeStamp` of v1 is left at `-1`, the broker uses its receive time.

Version 2, added by Kafka 0.9, replaced the per-partition `TimeStamp` with one `RetentionTime` for the whole request,
so **the partition entry of v2 has the layout of the v0 one again** and v1 is the odd version out. The retention is
handled in `KafkaApis.handleOffsetCommitRequest` @ 0.9.0.1:

* `RetentionTime = -1` (`OffsetCommitRequest.DEFAULT_RETENTION_TIME`) means "use the broker's own retention", i.e.
  `offsets.retention.minutes`, which defaults to 1440 (24 hours);
* any other value replaces that retention for this commit alone;
* the commit timestamp of the stored entry is always the receive time of the broker, and the expiry timestamp is
  `commitTimestamp + retention`. A v1 commit with an explicit `TimeStamp` counts its retention from that timestamp
  instead — that is the only thing the removed field could do.

Both were verified against the 0.9.0.1 broker of this branch by committing an offset and decoding the entry that
reached `__consumer_offsets` (value schema v1: offset, metadata, commit timestamp, expire timestamp):

```
retention_time = -1     -> commit = 1788893878450, expire = 1788980278450   (+86400000 ms, the broker default)
retention_time = 60000  -> commit = 1788893878452, expire = 1788893938452   (+60000 ms, as requested)
```

The offsets of an expired entry are removed by the coordinator's cleanup, which runs every
`offsets.retention.check.interval.ms` (600000 by default), not at the instant of the expiry timestamp.

Because the three versions have different fields, the request is described by three classes: `OffsetCommitRequest` is
v2, `OffsetCommitRequestV1` and `OffsetCommitRequestV0` only lower its `VERSION` constant, which the version-aware
`getScheme()` of the request and of its `OffsetCommitRequestTopic`/`OffsetCommitRequestPartition` DTOs follows. A
scheme is a static property of a class, so a version that changes the layout needs a class of its own.

`Client::commitGroupOffsets()` sends v2 when `offsets.storage = kafka` and v0 when it is `zookeeper`; the
`retention_time` it puts on the wire is the `offset.retention.ms` option of the consumer, `-1` by default.

Metadata longer than `offset.metadata.max.bytes` (4096 by default) is answered with the error code 12,
`OffsetMetadataTooLarge`, by every version - v0 checks it before writing to ZooKeeper, v1 and v2 filter the entry out
of the append to `__consumer_offsets`. **This behaves differently from 0.8.2.2**: there the rejected entry still
reached the in-memory cache of the coordinator and an immediate OffsetFetch read it back, while
`GroupMetadataManager.prepareStoreOffsets` @ 0.9.0.1 filters it out before both the append and the `putOffset` of
the cache. Verified on the broker of this branch with a 5000 character metadata: the commit answers 12 and the
OffsetFetch right after it answers the offset -1 with the error code 0, i.e. "never committed".

## OffsetFetch API (key 9, v0 and v1)

v0 and v1 are identical on the wire; v0 reads the offsets from ZooKeeper, v1 reads them from Kafka.

```
OffsetFetchRequest => ConsumerGroup [TopicName [Partition]]
  ConsumerGroup => string
  TopicName     => string
  Partition     => int32
```

```
OffsetFetchResponse => [TopicName [Partition Offset Metadata ErrorCode]]
  TopicName => string
  Partition => int32
  Offset    => int64
  Metadata  => string
  ErrorCode => int16
```

When no offset has been committed for a topic-partition, v1 does not set an error code — it returns offset `-1`,
empty metadata and the error code `0`. v0 reads a ZooKeeper node that does not exist and reports the same offset
`-1` with the error code `3`, `UnknownTopicOrPartition`; a client that fetches the starting position of a group has
to treat that code as "no offset yet", not as a failure.

**This is where 0.9.0.1 differs from 0.8.2.2.** A partition that the cluster does not host at all was answered with
the error code `3` by both versions on 0.8.2.2. On 0.9.0.1 only v0 still does: `KafkaApis.handleOffsetFetchRequest`
hands the whole list to the group coordinator for v1 and notes that "we do not need to filter the partitions in the
metadata cache as the topic partitions will be filtered in coordinator's offset manager through the offset cache" -
and a partition that the offset cache does not know is just an uncommitted one. Asking v1 for the partition 4242 of
a topic with three partitions therefore answers offset `-1`, empty metadata and the error code `0`, exactly like an
existing partition without a committed offset. A client cannot use OffsetFetch v1 to find out whether a partition
exists; Metadata is the api for that.

## ControlledShutdown API (key 7, v0 and v1)

This is the request that `kafka-server-stop.sh` triggers through `controlled.shutdown.enable`: the controller moves
every partition leader off the broker that is about to stop, so that no producer or consumer sees a leader election
timeout. It is a broker-to-controller request, not a client one, but nothing stops a client from sending it - and
version 0 of it is the one api of the protocol that a client cannot send with the common request header.

```
ControlledShutdownRequest v0 and v1 => BrokerId
  BrokerId => int32
```

```
ControlledShutdownResponse v0 and v1 => ErrorCode [TopicName Partition]
  ErrorCode => int16
  TopicName => string
  Partition => int32
```

**The version 0 request has no `ClientId`.** `ControlledShutdownRequest.readFrom` @ 0.9.0.1 reads the api version,
the correlation id, then the client id **only when `versionId > 0`**, and the broker id last; a client id string on
the wire would be read as the broker id by version 0. Version 1, added by Kafka 0.9, is the version that finally
uses the common header, so `ControlledShutdownRequest` (v1) keeps the `clientId` of its parent scheme and
`ControlledShutdownRequestV0` drops it, which makes the version 0 frame a mere 12 bytes long. A 0.9.0.1 broker
answers both, verified against the broker of this branch.

The response has no version of its own: `ControlledShutdownResponse` @ 0.9.0.1 is the same frame for both requests.
The array of the response holds the topic-partitions that still have a leader or a replica on the broker; an empty
array with the error code 0 means the broker may be stopped. Unlike every other response, these are flat pairs and
not partitions grouped by their topic, so one topic may appear several times.

Only the active controller serves the request, and a 0.9 Metadata response does not say which broker that is (the
`ControllerId` field arrived with version 1 of the Metadata api in Kafka 0.10) - a client has to try the brokers.

A broker id that the controller does not know is answered with the error code **8 (BrokerNotAvailable)** by a
0.9.0.1 broker, for both versions of the request: the controller throws `BrokerNotAvailableException` and
`ControlledShutdownRequest.handleError()` maps `e.getClass`. **This is a behaviour change against 0.8.2.2**, which
answered -1 (Unknown) in the very same situation, because that release mapped `e.getCause` - null for a directly
thrown exception - and `ErrorMapping.codeFor(null)` fell back to the Unknown code. The broker log shows the reason
either way:

```
ERROR [KafkaApi-0] error when handling request Name: ControlledShutdownRequest; Version: 1; CorrelationId: 21; ClientId: Some(t2); BrokerId: 4242
kafka.common.BrokerNotAvailableException: Broker id 4242 does not exist.
```

An unknown broker id is therefore a harmless way to probe the api, which is what the integration test does - asking
for a real broker id would shut that broker down.

## Group membership protocol (keys 11 to 14)

Kafka 0.9 moved the coordination of a consumer group out of ZooKeeper and into the broker: the group coordinator
that already held the committed offsets ("GroupCoordinator API (key 10, v0)" above) now also runs the membership
protocol. Its four apis are generic - the broker never looks into the payloads a member sends - and the
`protocol_type` of the JoinGroup request names the meaning of those bytes; `consumer` is the one this client
implements, see "Consumer group protocol" below.

Every request of the four goes to the coordinator of the group and nowhere else; a request that reaches another
broker is answered with the error code 16 (`NotCoordinatorForGroup`).

The state machine of `kafka/coordinator/GroupMetadata.scala` @ 0.9.0.1 has four states, and each of them answers
differently:

| State | Reached when | JoinGroup | SyncGroup | Heartbeat |
|-------|--------------|-----------|-----------|-----------|
| `PreparingRebalance` | A member joined, left or timed out | joins and waits for the other members | 27 `RebalanceInProgress` | 27 `RebalanceInProgress` |
| `AwaitingSync`  | Every member has rejoined | answered right away for an unchanged member | held until the leader sends its assignment | 27 `RebalanceInProgress` |
| `Stable`        | The leader's assignment was stored | rebalances, unless a follower rejoins unchanged | returns the stored assignment | 0 |
| `Dead`          | The group was removed from this coordinator | 25 `UnknownMemberId` | 25 `UnknownMemberId` | 25 `UnknownMemberId` |

The generation of a group starts at **1** and is incremented with every rebalance. A member id is assigned by the
coordinator as `<client id>-<random uuid>` (`GroupCoordinator.doJoinGroup` @ 0.9.0.1), e.g.
`t3-069f4b14-6878-407e-a708-a9288ca8b251` for the client id `t3`, so the client id of a member is visible in the
group forever; it is not otherwise interpreted.

The whole cycle of one generation, as the integration test
[`tests/Integration/GroupMembershipApiTest.php`](../../tests/Integration/GroupMembershipApiTest.php) drives it
against a real broker:

```
GroupCoordinator -> JoinGroup(member_id = "") -> member id, generation 1, the leader and the members
   leader:   SyncGroup(assignment of every member) -> its own assignment
   follower: SyncGroup([])                          -> its own assignment, once the leader has sent one
   both:     Heartbeat  ... every heartbeat.interval.ms, 0 while the group is stable
             Heartbeat  -> 27 as soon as another member joins or leaves: rejoin with JoinGroup
             LeaveGroup -> 0, the group rebalances right away instead of after the session timeout
```

## JoinGroup API (key 11, v0)

```
JoinGroupRequest => GroupId SessionTimeout MemberId ProtocolType [GroupProtocol]
  GroupId        => string
  SessionTimeout => int32
  MemberId       => string
  ProtocolType   => string
  GroupProtocol  => ProtocolName ProtocolMetadata
    ProtocolName     => string
    ProtocolMetadata => bytes
```

```
JoinGroupResponse => ErrorCode GenerationId GroupProtocol LeaderId MemberId [Member]
  ErrorCode     => int16
  GenerationId  => int32
  GroupProtocol => string
  LeaderId      => string
  MemberId      => string
  Member        => MemberId MemberMetadata
    MemberId       => string
    MemberMetadata => bytes
```

The `RebalanceTimeout` that `main` sends between `SessionTimeout` and `MemberId` is a field of **version 1**
(Kafka 0.10.1) and must not be sent to a 0.9 broker, which drops the frame without an answer.

A client that has no member id yet sends an **empty** `MemberId` and receives the one the coordinator assigned to
it; a member that rejoins has to send the id of the previous generation, otherwise the coordinator answers 25
(`UnknownMemberId`) and the client has to join again with an empty id. `SessionTimeout` has to lie between
`group.min.session.timeout.ms` and `group.max.session.timeout.ms` of the broker - 6000 and 30000 by default, 1000
and 60000 on the container of this branch - and is answered with 26 (`InvalidSessionTimeout`) otherwise.

`GroupProtocol` lists the protocols the member supports, best first; the coordinator picks the first one that
*every* member of the group supports and reports it as the `GroupProtocol` of the answer. A member that offers none
of them, or another `ProtocolType` than the group has, is refused with 23 (`InconsistentGroupProtocol`).

The `Member` array of the answer is filled **only for the leader** - the member whose id equals `LeaderId` - and
carries the metadata every member sent for the selected protocol; every other member receives an empty array and
waits for its assignment. The leader is simply the first member of the group's internal map, and it changes with a
rebalance.

**This request blocks, and it is the only one of the protocol that does.** The coordinator answers it only once
every known member of the group has rejoined, i.e. when the rebalance is complete, or once the members that did not
show up have missed their session timeout. A client therefore needs a socket read timeout - `request.timeout.ms` -
larger than its `session.timeout.ms`, as the Java client requires as well. Observed on the 0.9.0.1 container: the
join of the first member of a fresh group is answered immediately, the join of a second member is held until the
first member rejoins (it learns about the rebalance from the error code 27 of its next heartbeat).

An error answer carries the generation **0** - not the `UNKNOWN_GENERATION_ID` of -1 that the Java client uses for
a member without a generation, `GroupCoordinator.joinError` @ 0.9.0.1 builds the answer with `generationId = 0` -
an empty `GroupProtocol`, an empty `LeaderId`, the `MemberId` that was sent and an empty member array.

The `Member` array comes out of the internal map of the coordinator and is **not** ordered by the moment the
members joined; a leader that needs a stable order - a range assignor does - has to sort it itself. Verified on the
0.9.0.1 container: after a rebalance the leader received the two members in the opposite order of their joins.

## SyncGroup API (key 14, v0)

```
SyncGroupRequest => GroupId GenerationId MemberId [GroupAssignment]
  GroupId         => string
  GenerationId    => int32
  MemberId        => string
  GroupAssignment => MemberId MemberAssignment
    MemberId         => string
    MemberAssignment => bytes
```

```
SyncGroupResponse => ErrorCode MemberAssignment
  ErrorCode        => int16
  MemberAssignment => bytes
```

The `ThrottleTimeMs` that opens the response on `main` is a field of **version 1** (Kafka 0.10.1) and is not part of
this protocol.

Every member sends SyncGroup right after its JoinGroup answer, but only the leader fills `GroupAssignment`: it
computes the assignment of the whole generation out of the members it received and hands the coordinator one byte
array per member. The coordinator stores them and answers every member with its own share; the answers of the
members that synced before the leader are held until the leader's request arrives. A member the leader did not
mention receives an **empty** assignment (`GroupCoordinator.doSyncGroup` @ 0.9.0.1 fills the missing members in),
which is how a consumer learns that it got no partitions.

A generation that is not the current one is answered with 22 (`IllegalGeneration`), a member id the group does not
have with 25 (`UnknownMemberId`), and a group that started to rebalance in the meantime with 27
(`RebalanceInProgress`). Every error answer carries an empty `MemberAssignment`.

## Heartbeat API (key 12, v0)

```
HeartbeatRequest => GroupId GroupGenerationId MemberId
  GroupId           => string
  GroupGenerationId => int32
  MemberId          => string
```

```
HeartbeatResponse => ErrorCode
  ErrorCode => int16
```

The error code is the whole answer, and it is how the coordinator drives the client: `0` means the member is alive
and its session timeout has been reset, 27 (`RebalanceInProgress`) that the group is rebalancing and the member has
to send JoinGroup again, 25 (`UnknownMemberId`) that the coordinator dropped it - after a missed session timeout,
for instance - and 22 (`IllegalGeneration`) that its generation is over. A heartbeat has to be sent within
`session.timeout.ms`; the Java client uses `heartbeat.interval.ms` (a third of it) and so does this one, from its
poll loop, because PHP has no background thread.

The order of the checks in `GroupCoordinator.handleHeartbeat` @ 0.9.0.1 is worth knowing: the state of the **group**
is checked before the member, so a heartbeat of an unknown member of a group that is rebalancing is answered 27 and
not 25. While the coordinator is still loading the group out of `__consumer_offsets` it answers `0` "blindly", so a
successful heartbeat is not a proof of membership either.

## LeaveGroup API (key 13, v0)

```
LeaveGroupRequest => GroupId MemberId
  GroupId  => string
  MemberId => string
```

```
LeaveGroupResponse => ErrorCode
  ErrorCode => int16
```

Removing the member starts a rebalance right away, instead of after the session timeout of a member that simply
stopped answering; for a consumer that means that its partitions are reassigned to the other members within
milliseconds. This is what a consumer sends when it shuts down in an orderly way.

A member id the coordinator does not know - because the member already left, or because the group does not exist at
all - is answered with 25 (`UnknownMemberId`). Leaving the last member of a group leaves an empty group behind that
`ListGroups` still reports until its offsets expire.

## Consumer group protocol (protocol_type = consumer)

The group membership apis of 0.9 are deliberately generic: the coordinator knows a group by its `protocol_type` and
by the list of `protocol_name`s its members support, and it moves the `member_metadata` and `member_assignment`
byte arrays between the members without looking inside them. Everything a *consumer* group agrees on therefore
lives in the two structures below, which the broker never parses - `ConsumerProtocol` of the Java client of
0.9.0.1, `kafka.coordinator.GroupMetadata` treating both fields as opaque `bytes`.

A consumer group announces `protocol_type = "consumer"` in its JoinGroup request; a `protocol_name` is the name of
the partition assignor - `range` or `roundrobin` for the two built-in ones - and the coordinator picks a name that
every member of the group supports, answering with the error **23 (InconsistentGroupProtocol)** when there is none.

```
Subscription => Version [Topic] UserData
  Version  => int16
  Topic    => string
  UserData => bytes
```

```
MemberAssignment => Version [Topic [Partition]] UserData
  Version   => int16
  Topic     => string
  Partition => int32
  UserData  => bytes
```

A member packs a `Subscription` into the `member_metadata` of its JoinGroup request. The coordinator elects one
member as the leader and hands it every member's metadata in the `members` array of the JoinGroup response; the
leader runs the assignor on them and sends one `MemberAssignment` per member in its SyncGroup request, from which
every member gets its own back in the SyncGroup response.

Both structures start with a version, and Kafka 0.9.0.1 only ever writes **0**. The Java client parses a higher
version with the layout of version 0 and ignores whatever follows the fields it knows, so a later version may only
append fields - which is exactly what 0.10 does not do, and why this line can pin the version to 0. This client
keeps the version it read, so a structure of an unknown version survives a decode and encode round trip.

`UserData` is the escape hatch of the protocol: a custom assignor can put anything into the `Subscription` it
builds - a rack id, the number of cpus of the machine, the assignment of the previous generation for a sticky
assignor - and reads it back in the assignment of the leader. The `bytes` primitive is nullable, but the Java
client of 0.9 defaults the field to an **empty byte array** (`00 00 00 00`, not `ff ff ff ff`) in both structures,
and so does this client; both accept the null form on the wire.

A member that the assignor left without partitions gets a complete structure with an **empty topic array**, not an
empty byte array: a Kafka 0.9.0.1 broker relayed `00 00 00 00 00 00 00 00 00 00` for the fourth member of a group
of four on a topic with three partitions.

### Assignors

| Name on the wire | Class | Rule |
|---|---|---|
| `range` (default) | `Consumer\RangeAssignor` | Per topic: its members sorted lexicographically, its partitions in numeric order, `partitions / members` partitions each, the first `partitions % members` members get one more. |
| `roundrobin` | `Consumer\RoundRobinAssignor` | All partitions of all subscribed topics - topics lexicographically, partitions numerically - handed out one by one to the next member, in lexicographic order of the member ids, that subscribes to the topic of the partition. |

Both are the assignors of the Java client of 0.9.0.1, with its ordering rules, so a PHP member may lead a group of
Java members and the other way round: with two members on one topic with three partitions, `range` gives the
lexicographically first member the partitions 0 and 1 and the second one the partition 2, while `roundrobin` gives
the first one 0 and 2 and the second one 1. The difference shows on a group that consumes many topics with few
partitions each: `range` puts the first partition of every topic on the same member, `roundrobin` spreads them.

`partition.assignment.strategy` selects one of the two by its wire name, or names a class that implements
`Consumer\PartitionAssignorInterface`; `Consumer\AbstractPartitionAssignor::fromStrategy()` resolves the option.
The name an assignor announces is what the group agrees on, so every member of a group has to use the same one.

The vectors of this section were captured from the members of three groups of `kafka-console-consumer.sh
--new-consumer` processes (Kafka 0.9.0.1, one topic with three partitions), read back with a raw DescribeGroups v0
frame:

```bash
docker exec kafka-0-9-0-1 sh -c 'printf "group.id=g\n" > /tmp/c.properties'
docker exec -d kafka-0-9-0-1 /opt/kafka/bin/kafka-console-consumer.sh --new-consumer \
    --bootstrap-server localhost:9092 --topic t6-consumer-protocol --consumer.config /tmp/c.properties
```

### Consumer group membership from `poll()`

PHP has no background thread, so everything the Java consumer does on its heartbeat thread happens inside
`KafkaConsumer::poll()` on this branch. What that means for an application, as
[`Consumer\Internals\ConsumerCoordinator`](../../src/Kafka/Consumer/Internals/ConsumerCoordinator.php) implements it
and `tests/Integration/ConsumerGroupTest.php` verifies against the broker:

* **The first `poll()` after `subscribe()` joins the group**: GroupCoordinator → JoinGroup → (the leader runs the
  assignor) → SyncGroup → the positions of the assigned partitions, from their committed offsets or from
  `auto.offset.reset`. Nothing is sent by `subscribe()` itself.
* **Every further `poll()` sends a heartbeat** once `heartbeat.interval.ms` has elapsed since the last one. A
  consumer that does not poll for longer than `session.timeout.ms` is dropped by the coordinator, its partitions are
  given to the other members, and its next heartbeat is answered 25 (`UnknownMemberId`) — it then rejoins with a
  **new member id**. Keep the processing of a batch well below the session timeout, or raise
  `session.timeout.ms` within the `group.min.session.timeout.ms`/`group.max.session.timeout.ms` of the broker.
  There is no `max.poll.interval.ms` on this line: that option, and the rebalance timeout it needs, arrived with
  Kafka 0.10.1 (JoinGroup v1).
* **The error codes drive the state machine**, as in `AbstractCoordinator`/`ConsumerCoordinator` @ 0.9.0.1: 27
  (`RebalanceInProgress`) and 22 (`IllegalGeneration`) rejoin with the member id of the previous generation, 25
  rejoins without one, 15 and 16 look the coordinator up again. A rebalance that another rebalance interrupts is
  simply repeated instead of being reported to the application.
* **The positions are committed before the partitions are given up** in a rebalance, and a 22/25/27 on that commit
  does not keep the member from rejoining. A `Consumer\ConsumerRebalanceListener` passed to `subscribe()` sees the
  same two moments (`onPartitionsRevoked()`, `onPartitionsAssigned()`), which is where a consumer with
  `enable.auto.commit` off commits what it has processed.
* **`request.timeout.ms` has to exceed `session.timeout.ms`** — the coordinator holds a JoinGroup until every known
  member has rejoined, so the read timeout of the socket bounds the whole rebalance. `subscribe()` refuses a
  configuration that does not; the consumer default is 40000 against a session timeout of 30000, as in Java
  (`KafkaConsumer.java:556` @ 0.9.0.1). An `assign()`ed consumer joins no group and is not affected.
* **`unsubscribe()` and `close()` send LeaveGroup**, so the group rebalances at once instead of after a session
  timeout; `close()` commits first when `enable.auto.commit` is on.
* Because a JoinGroup blocks its connection until the rebalance is over, **two members of one group cannot share a
  PHP process**: the second member's join can only be written while the first one is waiting for its own answer.
  The integration suite therefore runs the second member in a child process
  (`tests/Fixture/consumer-group-member.php`).

## DescribeGroups API (key 15, v0)

Reports the state, the protocol and the members of the groups a broker coordinates. Together with
[ListGroups](#listgroups-api-key-16-v0) this is what `kafka-consumer-groups.sh --new-consumer --describe` uses, and
what `Admin\AdminClient::describeGroup()` sends.

```
DescribeGroupsRequest => [GroupId]
  GroupId => string
```

```
DescribeGroupsResponse => [ErrorCode GroupId State ProtocolType Protocol [MemberId ClientId ClientHost MemberMetadata MemberAssignment]]
  ErrorCode        => int16
  GroupId          => string
  State            => string
  ProtocolType     => string
  Protocol         => string
  MemberId         => string
  ClientId         => string
  ClientHost       => string
  MemberMetadata   => bytes
  MemberAssignment => bytes
```

The response has **no error code of its own**: every group carries one, and the groups come back in the order of the
request. An empty group array is legal and is answered with an empty group array.

A group has to be asked from **its own coordinator** ([GroupCoordinator](#groupcoordinator-api-key-10-v0)); another
broker answers that group with the error code 16 (NotCoordinatorForGroup) and an otherwise empty description. The
other error codes a group entry can carry are 15 (GroupCoordinatorNotAvailable, the coordinator is shutting down),
14 (GroupLoadInProgress, it is still reading `__consumer_offsets`) and 30 (GroupAuthorizationFailed).

`State` is one of the **five** states of `kafka/coordinator/GroupMetadata.scala` @ 0.10.2.2 — Kafka 0.10.1 added
`Empty` to the four of 0.9. This is what a 0.10.2.2 broker really answered while a group was driven through the
membership protocol:

| State                | When                                                              | ProtocolType | Protocol | Members |
|----------------------|-------------------------------------------------------------------|--------------|----------|---------|
| `PreparingRebalance` | a member joined or left and the coordinator waits for the others   | `consumer`   | `""`     | yes     |
| `AwaitingSync`       | every member has joined, the leader has not sent SyncGroup yet     | `consumer`   | `""`     | yes     |
| `Stable`             | the assignment is published, the members only send heartbeats      | `consumer`   | `range`  | yes     |
| `Empty`              | the last member has left, the committed offsets are still there    | `consumer`   | `""`     | no      |
| `Dead`               | the coordinator has never heard of the group, or has forgotten it  | `""`         | `""`     | no      |

`Protocol` is therefore only filled in while the group is `Stable`, exactly as `GroupMetadata.summary` says; every
other state answers `GroupCoordinator.NoProtocol`, the empty string.

**`Empty` is the state that Kafka 0.10.1 added, and it changes what "the group is gone" means.** A 0.9.0.1
coordinator dropped a group the moment its last member left: it disappeared from ListGroups and DescribeGroups
answered `Dead` for it, exactly as for a group that had never existed. From 0.10.1 on the group moves to `Empty`
instead and **lingers there with its committed offsets** until `offsets.retention.minutes` expires them; only the
periodic expiry task makes it `Dead` and removes it. In that state the coordinator

* still **lists** the group in ListGroups, with its protocol type,
* answers **JoinGroup normally**, so a new member simply takes the group over and rebalances it (`Empty` →
  `PreparingRebalance` is a legal transition, and it is the only one out of `Empty` that is not death),
* answers SyncGroup, Heartbeat, LeaveGroup and OffsetCommit with 25 (`UnknownMemberId`) — there is no member to
  speak for —
* and still answers **OffsetFetch**, which is what makes a restarted consumer of the same group resume where the
  group committed.

A group that only uses Kafka to store offsets and never joins is in `Empty` from the start, which is the second
reason the state exists.

A client can therefore tell "everybody left" (`Empty`) from "never existed" (`Dead`) on this line, which it could
not on 0.9.

**An unknown group is not an error.** A group the coordinator has never heard of is answered with the error code 0,
the state `Dead`, an empty protocol type, an empty protocol and no members - `GroupCoordinator.handleDescribeGroup()`
returns its `DeadGroup` summary for it.

`ClientHost` is the address of the connection the member joined over, in the notation of Java's
`InetAddress.toString()`, i.e. with a leading slash: `/172.18.0.1`. `MemberMetadata` and `MemberAssignment` are the
opaque byte arrays of the protocol type: for `consumer` groups they hold the `Subscription` the member sent with its
JoinGroup request and the `MemberAssignment` the leader published with SyncGroup.

## ListGroups API (key 16, v0)

Lists the groups a broker is the coordinator of.

```
ListGroupsRequest =>
```

```
ListGroupsResponse => ErrorCode [GroupId ProtocolType]
  ErrorCode    => int16
  GroupId      => string
  ProtocolType => string
```

The request has **no body at all**, only the common request header - the frame is 12 bytes plus the client id.

The error code belongs to the whole request: `GroupCoordinator.handleListGroups()` @ 0.9.0.1 answers 15
(GroupCoordinatorNotAvailable) while the coordinator is shutting down and 14 (GroupLoadInProgress) while it is still
reading the `__consumer_offsets` partitions it owns, both with an empty group array; the authorizer answers 31
(ClusterAuthorizationFailed).

Every broker only reports **the groups it coordinates itself**, and the groups of a cluster are spread over the
partitions of `__consumer_offsets`, so the list of the whole cluster is the union of the answers of every broker -
that is what `Admin\AdminClient::listAllGroups()` does. A group appears here as soon as it has a member and stays
until the coordinator forgets it, which on Kafka 0.10.1 and later is **not** the moment its last member leaves: the
group lingers in the state `Empty` with its committed offsets until `offsets.retention.minutes` expires them, and it
is listed all that time (a 0.9.0.1 broker dropped it at once - see the DescribeGroups section). The entry says
nothing about the state of the group, DescribeGroups does.

## CreateTopics API (key 19, v0 and v1)

Creates topics through the protocol instead of writing to ZooKeeper. The api arrived with Kafka **0.10.1**; a
0.10.2.2 broker serves the versions **0 and 1**.

```
CreateTopicsRequest => [CreateTopicRequest] Timeout [ValidateOnly]
  CreateTopicRequest => Topic NumPartitions ReplicationFactor [ReplicaAssignment] [Config]
    Topic             => string
    NumPartitions     => int32
    ReplicationFactor => int16
    ReplicaAssignment => PartitionId [Replica]
      PartitionId => int32
      Replica     => int32
    Config            => ConfigKey ConfigValue
      ConfigKey   => string
      ConfigValue => string
  Timeout      => int32
  ValidateOnly => boolean   # v1 only
```

```
CreateTopicsResponse => [TopicError]
  TopicError => Topic ErrorCode [ErrorMessage]
    Topic        => string
    ErrorCode    => int16
    ErrorMessage => nullable string   # v1 only
```

Version 1 adds exactly two fields (`CREATE_TOPICS_REQUEST_V1` / `CREATE_TOPICS_RESPONSE_V1` in `Protocol.java` @
0.10.2.2): the trailing `ValidateOnly` of the request - the first **boolean** of the protocol this client sees, a
single byte, `00` or `01` - and the `ErrorMessage` of every topic of the answer, which is the message of the
exception the controller caught. The topic entry of the request is byte for byte the one of version 0
(`SINGLE_CREATE_TOPIC_REQUEST_V1 = SINGLE_CREATE_TOPIC_REQUEST_V0`).

**Only the active controller serves this api.** `KafkaApis.handleCreateTopicsRequest` @ 0.10.2.2 answers every topic
of the request with the error code 41 (NotController) when `controller.isActive` is false, before it looks at the
request at all. Metadata v0 does not name the controller, so this client finds it by asking - see the DeleteTopics
section below and `Admin\AdminClient::findController()`.

A topic is described in **one of two ways**, and mixing them is an error:

* `NumPartitions` and `ReplicationFactor` are set and the assignment array is **empty**: the controller places the
  replicas with `AdminUtils.assignReplicasToBrokers`;
* both are `-1` (`CreateTopicsRequest.NO_NUM_PARTITIONS` / `NO_REPLICATION_FACTOR`) and the assignment array names
  the broker ids of every partition, the preferred leader first.

Setting both is answered with **42 (InvalidRequest)** and the message *"Both numPartitions or replicationFactor and
replicasAssignments were set. Both cannot be used at the same time."*, which is the check at the top of
`AdminManager.createTopics`. The broker deliberately does **not** verify that an explicit assignment names brokers
that exist ("we don't check that replicaAssignment contains unknown brokers - unlike in add-partitions case, this
follows the existing logic in TopicCommand"): a topic assigned to a broker id that no broker has is written to
ZooKeeper, never gets a leader, and the request answers **7 (RequestTimedOut)** after `Timeout` - the topic then
exists in ZooKeeper but never appears in the metadata of the cluster, and DeleteTopics answers 3 for it.

`Timeout` is how long the **controller** waits for the topic to be created on it before it answers, not a socket
timeout. `Values <= 0 will trigger topic creation and return immediately`: the answer arrives at once and reports
**7 (RequestTimedOut)** for every topic that was accepted, although the creation is under way and finishes shortly
afterwards (observed: the topic is in the metadata of the broker ~50 ms later). The same is true for a timeout that
is simply too short. A successful answer means the topic exists **on the controller**; the other brokers learn about
it with the next metadata update, so a Metadata request may still answer 5 (LeaderNotAvailable) for a moment.

`ValidateOnly` runs the whole validation - the topic name, the replica placement, every topic-level option - and
answers without writing anything to ZooKeeper (`AdminUtils.validateCreateOrUpdateTopic` instead of
`createOrUpdateTopicPartitionAssignmentPathInZK`). A validated topic comes back with the error code **0** and does
not exist afterwards. Version 0 has no such flag, and the Java client refuses to even build a version 0 request with
it set.

Error codes observed on the 0.10.2.2 container, with the `ErrorMessage` that version 1 carries:

| Code | Name                     | Request that produces it                          | ErrorMessage                                                                 |
|------|--------------------------|---------------------------------------------------|------------------------------------------------------------------------------|
| 0    | None                     | The topic was created (or validated)              | `null`                                                                       |
| 7    | RequestTimedOut          | `Timeout` of 0, or an assignment to an unknown broker | `null`                                                                   |
| 17   | InvalidTopicException    | A topic name outside `[a-zA-Z0-9._-]`             | `topic name ... is illegal, contains a character other than ASCII alphanumerics, '.', '_' and '-'` |
| 36   | TopicAlreadyExists       | A topic of that name exists                       | `Topic 'x' already exists.`                                                  |
| 37   | InvalidPartitions        | `NumPartitions` = 0                               | `number of partitions must be larger than 0`                                 |
| 38   | InvalidReplicationFactor | `ReplicationFactor` larger than the broker count  | `replication factor: 2 larger than available brokers: 1`                     |
| 40   | InvalidConfig            | An unknown topic-level option **name**            | `Unknown Log configuration nope.ms.`                                         |
| 41   | NotController            | Sent to a broker that is not the controller       | `null`                                                                       |
| 42   | InvalidRequest           | Partitions/factor **and** an explicit assignment; the same topic twice in one request | see above          |
| 44   | PolicyViolation          | A `create.topic.policy.class.name` refused it     | the message of the policy                                                    |

**Quirk: an unparsable option VALUE is not 40.** `LogConfig.validate` first calls `validateNames`, which throws
Kafka's own `InvalidConfigurationException` - an `ApiException`, mapped to 40 - for an unknown option name, and then
`configDef.parse`, which throws the plain `ConfigException` of the common config framework. That one is not an
`ApiException`, so `Errors.forException` falls through to **-1 (Unknown)**: `retention.ms=soon` is answered with the
code -1 and the message `Invalid value soon for configuration retention.ms: Not a number of type LONG`. Only the
name of an option is reported as 40.

**Quirk: duplicates are handled by the broker, not by the schema.** The wire format is an array, so the same topic
can appear twice in one request; `CreateTopicsRequest.duplicateTopics` collects those and `KafkaApis` answers each
of them with 42 (InvalidRequest) and a message that names them. This client keys its topic map by name and therefore
cannot produce such a frame.

## DeleteTopics API (key 20, v0)

Deletes topics through the protocol. The api arrived with Kafka **0.10.1**; a 0.10.2.2 broker serves **v0** only.

```
DeleteTopicsRequest => [Topic] Timeout
  Topic   => string
  Timeout => int32
```

```
DeleteTopicsResponse => [TopicErrorCode]
  TopicErrorCode => Topic ErrorCode
    Topic     => string
    ErrorCode => int16
```

The request is a plain array of topic **names**, not of structures, and the answer carries the bare
`TOPIC_ERROR_CODE` entries - there is no `ErrorMessage` in this api at all, the reason of a failure is only in the
log of the broker.

**Only the active controller serves it**, exactly like CreateTopics: `KafkaApis.handleDeleteTopicsRequest` @
0.10.2.2 answers every topic of the request with 41 (NotController) when `controller.isActive` is false.

**Quirk: an empty topic array is answered by every broker with an empty array.** The handler builds the answer by
mapping over the topics of the **request** (`deleteTopicRequest.topics.asScala.map { topic => (topic,
Errors.NOT_CONTROLLER) }`), so a request without topics produces an answer without entries - on the controller and
on every follower alike. An empty DeleteTopics is therefore useless as a controller probe, and
`Admin\AdminClient::findController()` sends a request that names **one topic whose name can never be legal**
(`#kafka-client-controller-probe#` - `Topic.validate` only allows `[a-zA-Z0-9._-]`) instead: the controller cannot
find it in its metadata cache and answers 3 (UnknownTopicOrPartition) without touching ZooKeeper, every other broker
answers 41 for it, and nothing can ever be deleted by the probe. Verified against the container: the empty request
`00 00 00 00 00 00 00 00` comes back as `00 00 00 00`, the named one as one entry with the code 3.

**Deletion is asynchronous.** `AdminUtils.deleteTopic` only writes the topic into `/admin/delete_topics` in
ZooKeeper; the controller then stops the replicas and removes the partitions. `Timeout` is how long the controller
waits for that before it answers, and `Values <= 0 will trigger topic deletion and return immediately` - the answer
is then **7 (RequestTimedOut)** for every topic whose deletion was started. Measured on the single-broker container
with `delete.topic.enable=true`:

* `Timeout = 30000`: the controller answered **0** after ~60 ms, and the topic was gone from a Metadata answer ~50 ms
  after that;
* `Timeout = 0`: the answer came back at once with **7**, and the topic was gone from Metadata ~50 ms later.

So even a successful answer only says that the controller is done; a client that waits for the topic to disappear
has to poll the metadata. A cluster whose brokers run with `delete.topic.enable=false` - the **default** of Kafka
0.10 - accepts the request the same way and never carries the deletion out.

| Code | Name                     | Request that produces it                                            |
|------|--------------------------|---------------------------------------------------------------------|
| 0    | None                     | The topic was deleted within `Timeout`                              |
| 3    | UnknownTopicOrPartition  | The metadata cache of the broker has no such topic - also the answer to deleting the same topic a second time, once the first deletion finished |
| 7    | RequestTimedOut          | `Timeout` of 0, or a deletion that was not finished in time         |
| 29   | TopicAuthorizationFailed | The client may describe the topic but not delete it                 |
| 41   | NotController            | Sent to a broker that is not the controller                         |

A topic that is **already marked** for deletion is accepted again without an error: `AdminManager.deleteTopics`
swallows the `TopicAlreadyMarkedForDeletionException` "and still track[s] deletion allowing multiple calls to wait
for deletion".

## Transport security (SSL)

Kafka 0.9.0.0 replaced the single `port` of a broker with a list of **listeners**, one per security protocol
(`listeners=PLAINTEXT://0.0.0.0:9092,SSL://0.0.0.0:9093`). `SocketServer.scala` @ 0.9.0.1 opens one acceptor per
entry and remembers the protocol of every connection; from there on the two listeners are indistinguishable, they
run the same `KafkaApis` over the same request set. **No request or response changes a single byte because of the
transport**, which is why nothing above `IO\SocketStream` in this client knows that encryption exists.

A broker speaks TLS from the very first byte of a connection to its SSL listener: there is no in-protocol upgrade,
no `STARTTLS`-like request, and a plaintext request sent to 9093 is just an unparseable TLS record - the broker
drops the socket without an answer (verified: `tests/Integration/SslTransportTest.php`).

### Client configuration

| Option | Default | Notes |
|---|---|---|
| `security.protocol` | `PLAINTEXT` | `PLAINTEXT`, `SSL`, `SASL_PLAINTEXT`, `SASL_SSL`; the two SASL ones add the authentication of the "SASL/PLAIN" subsection below |
| `ssl.protocol` | `TLS` | `TLS`, `TLSv1_1`, `TLSv1_2`, `SSL`, `SSLv2`, `SSLv3` - the names of the Java client |
| `ssl.enabled.protocols` | - | list of the same values; when set it replaces `ssl.protocol` entirely |
| `ssl.ca.cert.location` | - | PEM bundle used as the trust anchor (`ssl.truststore.location` in Java) |
| `ssl.client.cert.location` | - | client certificate, only for `ssl.client.auth=required` brokers |
| `ssl.key.location` | - | private key of the client certificate |
| `ssl.key.password` | - | passphrase of that key |

`SocketStream` connects the TCP socket first and calls `stream_socket_enable_crypto()` on it afterwards, with the
crypto method that `ssl.enabled.protocols`/`ssl.protocol` map to. The stream context always carries
`verify_peer`, `verify_peer_name` and `peer_name`, so the certificate of the broker is verified and has to match
the host that was dialled; a failed handshake becomes a `NetworkException` carrying the OpenSSL message.

Two properties of PHP are worth recording, because neither is obvious:

* the handshake is bounded by the **connection timeout** the stream was created with, not by `request.timeout.ms` -
  the OpenSSL loop of PHP keeps the deadline the socket was opened with;
* `TLSv1_1` alone is refused by a current OpenSSL build (`no protocols available`) even though the 0.9 broker offers
  it, because the default security level of OpenSSL 3 rejects TLS below 1.2. `TLS` (the default) and `TLSv1_2`
  negotiate TLSv1.2 against a default-configured 0.9.0.1 broker.

### Metadata answers with the endpoint of the listener it arrived on

Version 0 of the Metadata api - the only version 0.9 has - carries exactly **one** `Host`/`Port` pair per broker,
so a single response cannot describe both listeners. `KafkaApis.handleTopicMetadataRequest` @ 0.9.0.1 resolves that
with the protocol of the connection the request came in on:

```scala
val response = new TopicMetadataResponse(
    brokers.map(_.getBrokerEndPoint(request.securityProtocol)), topicMetadata ++ unauthorizedTopicMetaData, ...)
```

and `getTopicMetadata(authorizedTopics, request.securityProtocol)` does the same for the leader/replica endpoints.

Verified against the broker of `docker/kafka-0.9.0.1`, which advertises
`PLAINTEXT://127.0.0.1:9092,SSL://127.0.0.1:9093`: the identical Metadata request answers with broker `#0` at
`127.0.0.1:9092` on the plaintext connection and with broker `#0` at `127.0.0.1:9093` on the encrypted one.

The consequence for a client is that **the security protocol is a property of the whole client, not of a single
connection**: a client that bootstraps over TLS discovers TLS endpoints and keeps its configuration for every
connection it opens to them, and there is no way for it to fall back to plaintext by accident - the plaintext port
never appears in what it learned. This client gets that for free because the same configuration array reaches
`Cluster` -> `Node::getConnection()` -> `ConnectionFactory` -> `SocketStream`; the connection cache is keyed by the
security protocol as well, so a plaintext and an encrypted connection to one `host:port` can never be confused.

### SASL/PLAIN

Kafka 0.9 already shipped SASL, but only the GSSAPI (Kerberos) mechanism, and the exchange happened *outside* the
protocol: the broker expected the raw token exchange on a freshly opened connection, with nothing framing it and no
way to negotiate a mechanism. **Kafka 0.10.0 (KIP-43) put the negotiation inside the protocol** with the
`SaslHandshake` request (api key 17, v0) and added the PLAIN mechanism, which is what makes SASL implementable in
pure PHP: PLAIN is a single token carrying a user name and a password, no Kerberos ticket in sight.

A `SASL_PLAINTEXT` or `SASL_SSL` connection therefore has three phases (`SaslServerAuthenticator.authenticate()` @
0.10.2.2, states `HANDSHAKE_REQUEST -> AUTHENTICATE -> COMPLETE`):

```
client                                     broker (SASL_PLAINTEXT://9094, SASL_SSL://9095)
  |                                                                 |
  |-- TCP connect ------------------------------------------------->|
  |-- TLS handshake (SASL_SSL only) ------------------------------->|
  |                                                                 |
  |-- Size ApiKey=17 ApiVersion=0 CorrelationId ClientId "PLAIN" -->|   an ordinary Kafka request
  |<-- Size CorrelationId ErrorCode=0 EnabledMechanisms=["PLAIN"] --|   an ordinary Kafka response
  |                                                                 |
  |-- Size "\0<username>\0<password>" ----------------------------->|   NOT a request: no header at all
  |<-- Size=0 ------------------------------------------------------|   the empty token, exchange complete
  |                                                                 |
  |-- Metadata, Produce, Fetch, ... ------------------------------->|   the connection is now ordinary
```

Only the **handshake** is a Kafka request. The tokens after it are bare frames: an `INT32` length followed by that
many bytes, which is precisely the `bytes` primitive of the protocol - no api key, no api version, no correlation
id, no client id. The broker reads them with a plain `NetworkReceive` and hands the payload to
`SaslServer.evaluateResponse()`; the `SaslAuthenticate` request (api key 36) that wraps the very same tokens into a
framed request with an error code is **Kafka 1.0** and must not be sent to a 0.10 broker.

For PLAIN the exchange is one round trip. The client token is the RFC 4616 message `authzid \0 authcid \0 passwd`,
which `PlainSaslServer.evaluateResponse()` splits on the NUL bytes into exactly three parts - this client always
sends an empty authorization id, as the Java `PlainLoginModule` does - and the answer is
`new byte[0]`, i.e. the four bytes `00 00 00 00` of an empty frame. The credentials travel in clear text inside the
token, so `SASL_PLAINTEXT` is only sound on a trusted network; `SASL_SSL` performs the identical exchange inside
the TLS channel and is the same code path plus the `ssl.*` options.

#### Client configuration

| Option | Default | Notes |
|---|---|---|
| `security.protocol` | `PLAINTEXT` | `SASL_PLAINTEXT` and `SASL_SSL` authenticate; `SASL_SSL` also takes every `ssl.*` option |
| `sasl.mechanism` | `PLAIN` | the only implemented mechanism, see below |
| `sasl.username` | - | the `authcid` of the token, `user_<name>` in the JAAS file of the broker |
| `sasl.password` | - | sent in clear text inside the token |

The JAAS configuration of the Java client (`sasl.jaas.config`, or a `KafkaClient` login module named by
`java.security.auth.login.config`) is **not** reproduced: a login module is a Java class, and PHP has no JAAS. The
two options above are the whole equivalent of the `username`/`password` of `PlainLoginModule`. An empty or missing
one is refused before a socket is opened, because a broker would only answer it by dropping the connection.

Of the four mechanisms a 0.10.2.2 broker can enable, this client performs `PLAIN` only. `GSSAPI` needs a Kerberos
binding, which PHP has neither in core nor as a maintained extension that could produce tokens a broker accepts;
`SCRAM-SHA-256` and `SCRAM-SHA-512`, added by 0.10.2 (KIP-84), need the multi-round exchange of RFC 5802 with
SASLprep-normalized credentials, which is a mechanism of its own and is out of scope here. Both are refused with an
`InvalidConfigurationException` that names the reason rather than being sent to the broker.

#### What the broker does, observed on `docker/kafka-0.10.2.2`

Every one of these was observed on the running container, and all but the version probe of the last-but-one row are
asserted by `tests/Integration/SaslTransportTest.php`. None of them produces an error code, because before Kafka 1.0
the only error code of the whole exchange is the one of the handshake response:

| Situation | Broker behaviour |
|---|---|
| handshake with an enabled mechanism | `ErrorCode = 0`, `EnabledMechanisms = ["PLAIN"]` |
| handshake with a mechanism it has not enabled | `ErrorCode = 33` (UnsupportedSaslMechanism) with the enabled ones, **then the connection is closed** |
| token with a wrong password, or for an unknown user | the connection is **closed during the token exchange**, without any answer (`SaslException` -> `IOException`) |
| any request other than the handshake as the first frame | the connection is closed without an answer - the broker parses the first frame as a handshake (or as a GSSAPI token, see below) and gives up |
| a second `SaslHandshake` on the same connection | the connection is closed: the state machine is past `HANDSHAKE_REQUEST` |
| `SaslHandshake` **v1** | the connection is closed - a 0.10.2.2 broker serves version 0 only |
| `ApiVersions` (api key 18) before the handshake | **answered normally**, with the full api-version list; it is the one request a 0.10.2 broker serves before authentication (KIP-35), so a client may probe the versions of a broker it has not authenticated to |

A client can therefore not tell a rejected password from a broker that died, which is why this client raises a
`SaslAuthenticationException` (client-side, no wire code) instead of the bare `NetworkException` of the dropped
socket: retrying it is pointless. The dedicated error code 58 (SaslAuthenticationFailed) arrived with Kafka 1.0.

The first frame of a connection is ambiguous on purpose: `SaslServerAuthenticator` @ 0.10.2.2 accepts either a
`SaslHandshake` request or a raw GSSAPI token there (`GSSAPI_OR_HANDSHAKE_REQUEST`), so that a 0.9 client, which
knows nothing about the handshake, can still authenticate with Kerberos against a 0.10 broker. That is why an
unparseable first frame is dropped silently rather than answered with an error: the broker cannot know whether it
was a malformed request or a token of a mechanism it does not have.

The endpoint property of the section above holds for the SASL listeners as well: the identical Metadata request
answers with `127.0.0.1:9094` on a `SASL_PLAINTEXT` connection and with `127.0.0.1:9095` on a `SASL_SSL` one, so a
client that bootstraps over SASL discovers the SASL endpoints of the cluster and keeps authenticating to every
broker it learns about. The connection cache is keyed by the security protocol **and** the user name, so two
clients with different credentials never share a connection.

## Cluster readiness

**This is one of the things Kafka 0.10 quietly fixed.** On the two lines below, a broker that had just started
answered a Metadata request with an **empty broker array** and kept doing so until some topic existed: the broker
list of a Metadata response comes from the metadata cache of the broker, that cache is only filled once the
controller has pushed an `UpdateMetadata` request to it, and on a cluster without a single topic that never
happened. Clients had to treat an empty broker array as "not ready, retry", never as "the cluster has no brokers".

A **0.10.2.2** broker fills its cache with the live brokers as soon as the controller has elected itself, with or
without topics. `KafkaApis.handleTopicMetadataRequest` @ 0.10.2.2 answers with `metadataCache.getAliveBrokers`, and
that is populated from the very first `UpdateMetadata` the controller sends on broker startup. Verified on a
throwaway container of the image of this branch, started empty and asked before anything else touched it:

```
Metadata v0, empty topic array:  brokers = 1, topics = 0
Metadata v1, null topic array:   brokers = 1, topics = 0
```

Two consequences, and neither of them makes the readiness probe obsolete:

* An empty broker array is **still** not "the cluster has no brokers" — it is "this broker has not caught up yet",
  and a broker that is still starting, or one whose controller connection has just been re-established, can answer
  it for a moment. `tests/Fixture/ClusterReadinessProbe.php` and `Cluster::bootstrap()` keep retrying it, and the
  probe costs nothing when the first answer is already complete.
* A **fresh topic** still answers 5 (`LeaderNotAvailable`) or 6 (`NotLeaderForPartition`) for a moment after it has
  been created, exactly as on 0.8 and 0.9, because the leader election is asynchronous. Every helper that creates a
  topic retries those two codes.

Note that readiness is not covered by a TCP health check either: the broker accepts connections on 9092 long before
it has registered itself with ZooKeeper.

## Broker quirks and observations

Everything a Kafka 0.10.2.2 broker does that a client cannot read out of the protocol grammar, collected from the
integration suite of this branch. The section that describes each item in detail is named behind it. An item marked
**(0.10)** is a change against the 0.9.0.1 line, whose own list is in `docs/protocol/0.9.0.md` on `0.9.x`.

**Framing and api surface**

* **(0.10) An api the broker cannot parse costs the connection.** The broker closes the socket - `docker logs
  kafka-0-10-2-2` shows `Closing socket for ... because of error` with the `InvalidRequestException` or
  `SchemaException` that caused it - where a 0.9.0.1 broker dropped the frame and kept the connection open, and a
  0.8.2.2 broker closed it. A **malformed body of a version the broker does serve** is punished the same way.
  → "An api the broker does not serve closes the connection".
* **(0.10) ApiVersions (18) is the one api whose unknown version is answered**, with the error code 35 and an empty
  api array, in the version 0 layout, on a connection that stays open. → "ApiVersions API (key 18, v0)".
* **(0.10) ControlledShutdown (7) is the last api that ignores its version.** It is still parsed by the Scala
  `ControlledShutdownRequest.readFrom()`, so the broker answers v0 (the header without a client id), v1 and
  anything above, although ApiVersions reports `MinVersion = MaxVersion = 1` for it. Every other api of the keys 0
  to 9 has lost that property since 0.9. → "The last Scala api does not check its version".
* **(0.10) SaslHandshake (17) on a non-SASL listener answers 34** (`IllegalSaslState`) with the enabled mechanisms,
  whatever mechanism was asked for: on a SASL listener the request never reaches the api layer, so everything
  `KafkaApis.handleSaslHandshakeRequest` sees is a handshake at the wrong moment.
* **(0.10) A broker without topics answers Metadata with its brokers**, where 0.8 and 0.9 answered zero brokers
  until a topic existed. An empty broker array is still "not ready, retry". → "Cluster readiness".
* **Metadata v0 answers with the endpoint of the listener the request arrived on**, one host/port per broker: a
  client that bootstraps over TLS learns the TLS endpoints of the whole cluster, one that bootstraps in plaintext
  learns the plaintext ones, and no request can ask one listener about the other.
  → "Metadata answers with the endpoint of the listener it arrived on".
* **An empty topic array means two different things.** In Metadata **v0** it asks for *every* topic of the cluster;
  in **v1** and above `[]` means "no topic at all" and `null` (`ff ff ff ff`) is what asks for every topic. A client
  that sends the v0 request unchanged as v1 gets an empty answer instead of the whole cluster.

**Offsets**

* **OffsetFetch v1 no longer validates the partition**: a partition the cluster does not host is answered with the
  offset `-1` and the error code `0` ("nothing committed"), where 0.8.2.2 answered 3. Version 0, which reads
  ZooKeeper, still answers 3. → "OffsetFetch API (key 9, v0 and v1)".
* **An oversized offset metadata never reaches the coordinator cache.** A commit whose metadata exceeds
  `offset.metadata.max.bytes` is answered 12 (`OffsetMetadataTooLarge`) and the entry is filtered out before the
  append *and* before the cache is updated, so an immediate OffsetFetch reports "never committed". A 0.8.2.2 broker
  cached it. Verified with a 5000 character metadata. → "OffsetCommit API (key 8, v0, v1 and v2)".
* **`RetentionTime` of OffsetCommit v2 counts from the commit.** `-1` asks for `offsets.retention.minutes` of the
  broker, any other value replaces it for that commit alone, and the expiry stored in `__consumer_offsets` is
  always `commitTimestamp + retention` with the commit timestamp being the receive time of the broker. Expired
  entries disappear at the next run of `offsets.retention.check.interval.ms`, not at the instant of the expiry.
  → "OffsetCommit API (key 8, v0, v1 and v2)".

**Group membership**

* **JoinGroup blocks.** The coordinator answers a JoinGroup only once every known member has rejoined, so
  `request.timeout.ms` has to exceed `session.timeout.ms`, and two members of a group cannot be driven from one
  single-threaded process. → "Group membership protocol (keys 11 to 14)".
* **An error answer of JoinGroup carries the generation 0**, not the `-1` of the Java client's
  `UNKNOWN_GENERATION_ID`: `GroupCoordinator.joinError` builds it with `generationId = 0` (the docblocks
  of `main` are wrong about this). → "JoinGroup API (key 11, v0)".
* **The `members` array of a JoinGroup answer is filled only for the leader**, and its order is the order of the
  coordinator's internal map, not the order in which the members joined. An assignor must therefore sort what it
  gets — both assignors of this client do. → "JoinGroup API (key 11, v0)".
* **Heartbeat checks the group before the member**: an unknown member of a rebalancing group is answered 27
  (`RebalanceInProgress`), not 25 (`UnknownMemberId`), and while the coordinator is loading the group it answers 0
  to everything. → "Heartbeat API (key 12, v0)".
* **A member id is `<client id>-<uuid>`** and the first generation of a group is **1**.
  → "Group membership protocol (keys 11 to 14)".
* **(0.10) A group whose last member leaves survives as `Empty`.** It keeps its committed offsets until
  `offsets.retention.minutes` expires them, is still listed by ListGroups, is described as `Empty` with its
  protocol type and no members, and answers JoinGroup normally so that a new member can take it over. A 0.9.0.1
  coordinator dropped such a group at once and answered `Dead` for it, which made "everybody left" and "never
  existed" indistinguishable. DescribeGroups still answers `Dead` with the error code 0 for a group that really
  does not exist, and `ClientHost` still arrives in Java's `InetAddress` notation, with a leading slash
  (`/172.18.0.1`). → "DescribeGroups API (key 15, v0)".

**Quotas, transport and the controller**

* **A quota never rejects anything**: the broker appends or reads and delays the *answer*, and reports the delay in
  the `ThrottleTime` of Produce v1 / Fetch v1. A throttled Fetch answer therefore arrives late, which a consumer
  with a short `fetch.max.wait.ms` can mistake for a timeout of its own — `Client::dispatch()` waits at most twice
  the `fetch.max.wait.ms` it sent. A fire-and-forget batch (`RequiredAcks = 0`) is throttled as well and never
  learns about it. → "Quotas and throttle time".
* **ControlledShutdown for a broker id the controller does not know answers 8** (`BrokerNotAvailable`), where
  0.8.2.2 leaked -1: `handleError()` maps `e.getClass` instead of `e.getCause`. It answers that for every version
  it is sent with. → "ControlledShutdown API (key 7, v0 and v1)".
* **The TLS handshake is bounded by the connection timeout of the stream**, not by `request.timeout.ms`, and
  OpenSSL 3 refuses `ssl.protocol = TLSv1_1` alone (`no protocols available`) even though the broker offers it,
  because its default security level rejects TLS below 1.2. → "Transport security (SSL)".

the container of `docker-compose.yml` runs without either, so those four are implemented from the specification and
not observed.

The codes 45 and above (`OUT_OF_ORDER_SEQUENCE_NUMBER`, `DUPLICATE_SEQUENCE_NUMBER`, the transaction codes) arrived
with Kafka 0.11 and are not on this branch.

## Wire vectors

Every frame below is a real frame of a real broker. A *request* vector is the frame this client sent and the broker
accepted, a *response* vector is the frame the broker sent back, byte for byte. The single exception is
`metadata.request.v0.all-topics`, which is built by the client (`source: constructed` in the vector file), because a
capture of the matching response would carry every topic of the test cluster.

**A vector is captured on the broker of the line that introduced the api version, and is not re-captured while the
frame does not change.** The api-key table above is what says whether it changed: a version that a 0.10.2.2 broker
still serves with the same schema still has the frame it had. Concretely:

* The version 0 apis were captured on Apache Kafka **0.8.2.2** with the topics `t10-vectors` and `t2-vectors` (three
  partitions each, replication factor 1) and the groups `t10-vectors-group`, `t10-vectors-zk` and
  `t2-vectors-group`.
* What Kafka 0.9 added was captured on the **0.9.0.1** container: Produce v1, Fetch v1, OffsetCommit v2 and
  ControlledShutdown v1, the four apis of the group membership protocol - JoinGroup, SyncGroup, Heartbeat and
  LeaveGroup, with the group `t3-vectors-group` and the client id `t3` - and the group apis DescribeGroups and
  ListGroups, with the topic `t4-vectors`, the group `t4-vectors-group` and one member that had joined with a raw
  JoinGroup and SyncGroup sequence. `controlledshutdown.response.v0` was re-captured there, because its error code
  for an unknown broker id changed from -1 to 8 between the two lines.
* What Kafka 0.10 adds is captured on the **0.10.2.2** container that `docker-compose.yml` builds. The first of
  those captures is `api-versions.json`: the ApiVersions request v0, the answer of the broker with the 21 keys it
  serves, and the answer to a request of the version 7, which is the error code 35 with an empty api array. All
  three were taken with the client id `kafka-client-t1-vectors` on a connection of their own; they need no topic and
  no group, because the api carries no state.

The last group of vectors is not made of frames at all: the payloads of the consumer group protocol
(`consumer-protocol.json`, `kind: structure`) are the contents of a `member_metadata` or `member_assignment` byte
array, without a `Size` field and without a header, captured on the 0.9.0.1 container with the topic
`t6-consumer-protocol` (three partitions) from groups of Java `kafka-console-consumer.sh` members.

The same bytes live in machine-readable form in [`vectors/`](vectors), one file per api, together with the values
that each frame decodes into. `tests/Compliance` replays all of them through the request and response classes -
decode the frame, compare every field of the scheme, encode the message back and compare the bytes - and
`DocumentationSyncTest` checks that the dumps below and the vector files still hold the same bytes. Neither half can
therefore drift away from the code:

```bash
vendor/bin/phpunit --testsuite compliance
```

Each line of a dump is `<bytes>   # <path of the field> = <value>`; the path is the one of the scheme, e.g.
`topics[t10-vectors].partitions[0].leader`. A line without a comment continues the bytes of the line above it.
