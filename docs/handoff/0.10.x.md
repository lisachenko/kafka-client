# Handoff: the 0.10.x line (Kafka 0.10.x)

State at handoff: the `0.9.x` line is **complete**. Everything a Kafka 0.9.0.1 broker speaks is implemented on the
`BinarySchema` engine and verified against a real broker — 790 unit tests, 67 compliance tests replaying 62 wire
vectors, 164 integration tests (`vendor/bin/phpunit` counts 1021 with the integration suite skipped). The grammar
is written down in [`docs/protocol/0.9.0.md`](../protocol/0.9.0.md), including a "Broker quirks and observations"
section that collects everything the protocol text does not tell.

The `0.10.x` branch as it stands today is the **pre-schema** implementation of the old mainline (commits
`5b6dd06..77993bc`): `pack()`/`unpack()` classes with Metadata v1/v2, Fetch v2/v3, Offsets v1, JoinGroup v1,
OffsetFetch v2, ApiVersions, SaslHandshake and a message format with timestamps. By rule 5 of
[`docs/CASCADE.md`](../CASCADE.md) that code is **dropped in the cascade merge** — it targets the removed
pack/unpack layer — and its features become the tickets below, re-implemented on the schema engine starting from
`main`'s classes. What the merge drops has to be listed in the merge commit and here.

Read `CLAUDE.md` first (hard rules, toolchain, the Composer/phpstan sandbox workaround, Docker).

## First decision for the owner: which Kafka release the line speaks

`0.8.x` speaks 0.8.2.2 and `0.9.x` speaks 0.9.0.1 — in both cases the **last** release of the line, and the
document below is written for **Kafka 0.10.2.2** on the same principle. That choice matters, because the 0.10 line
raised the protocol three times:

* **0.10.0** — message format v1 (timestamps, LZ4), Produce v2, Fetch v2, Metadata v1, ApiVersions (18),
  SaslHandshake (17), error codes 32–35.
* **0.10.1** — Fetch v3 (`max_bytes`), Offsets v1 (by timestamp), JoinGroup v1 (`rebalance_timeout`), Metadata v2
  (`cluster_id`), CreateTopics (19), DeleteTopics (20), error codes 36–42.
* **0.10.2** — OffsetFetch v2 (nullable topics, top-level error code), CreateTopics v1 (`validate_only`), error
  codes 43–44.

A branch that speaks 0.10.2.2 speaks all of it, and a broker of that version serves the lower versions as well.
If the owner prefers "0.10.0 only" (which is what the README of `0.9.x` currently says the `0.10.x` line tracks),
strike the 0.10.1 and 0.10.2 rows and keep the rest — nothing else in this plan changes.

## What Kafka 0.10.x adds over 0.9.0.1

Verified field by field against `clients/src/main/java/org/apache/kafka/common/protocol/{Protocol,ApiKeys,Errors}.java`
at the tag **0.10.2.2** (`git clone --depth 1 --branch 0.10.2.2 https://github.com/apache/kafka`), which is also the
authority for "unchanged" below. As always: the broker of the line has the last word, and the api-version probe of
`0.9.x` is replaced by a real **ApiVersions** request as soon as that api is implemented.

| Api | 0.9.0.1 | 0.10.x | Since | Start from `main` |
|---|---|---|---|---|

| Produce (0) | v0, v1 | **v2**: request body unchanged, response gains `log_append_time` int64 per partition (‑1 unless the topic uses `LogAppendTime`); the message set it carries is format v1 | 0.10.0 | `ProduceResponse`, `Data/ProduceResponsePartition` (`logAppendTime`), version-aware scheme as in `0.9.x` |
| Fetch (1) | v0, v1 | **v2**: identical schema, announces that the client understands message format v1. **v3**: request gains a top-level `max_bytes` int32 *after* `min_bytes`, and the partition order of the request becomes significant | v2: 0.10.0, v3: 0.10.1 | `FetchRequest`/`FetchResponse` |
| Offsets (2) | v0 | **v1**: request partition is `partition, timestamp` (no `max_num_offsets`), response partition is `partition, error_code, timestamp, offset` — **one** offset, not an array. `-1` = latest, `-2` = earliest, anything else = the first offset whose message timestamp is `>= t` | 0.10.1 | `OffsetsRequest`/`OffsetsResponse`, `Data/Offsets{Request,Response}Partition` |

Two engine-level consequences, both new to this project:

* **A `boolean` primitive** (`is_internal` of Metadata v1, `validate_only` of CreateTopics v1) — one byte, `00`/`01`.
  `BinarySchema` has no such type yet; add `TYPE_BOOLEAN` rather than smuggling it in as an int8.
* **Nullable arrays on the request side** (Metadata v1 topics, OffsetFetch v2 topics). The engine already knows
  `FLAG_NULLABLE` for arrays; make sure `null` writes `ff ff ff ff` and an empty array writes `00 00 00 00`, which
  are two *different* requests: null means "every topic", empty means "no topic".

## What to strip when cascading `0.9.x` into `0.10.x`

Rule 4 of `docs/CASCADE.md`: the lower line wins the shared part, the higher line's version-specific additions come
back on top as fields and constants. Concretely, on the `cascade/0.9.x-into-0.10.x` branch:

* **Drop** every pre-schema class of the current `0.10.x` (`src/Kafka/Protocol/**` with hand-written
  `pack()`/`unpack()`, the old `Record`/`RecordBatch`, the old consumer/producer), and record in the merge commit
  that the features they carried are the tickets below.
* **Keep from `0.9.x`**: the whole engine, framing, `Client`, `AdminClient`, `KafkaProducer`, `KafkaConsumer`,
  the group protocol, SSL, the test fixtures, the docs and the tooling.
* **Do not lower** anything: no 0.11 field (record batch v2, `throttle_time_ms` in SyncGroup/Heartbeat/LeaveGroup/
  DescribeGroups/ListGroups/OffsetCommit v3, transactions, `DeleteRecords` and the api keys above 20) may appear on
  this line, and `ApiKeys` must stop at **20**.
* `docs/protocol/0.9.0.md` is renamed to `docs/protocol/0.10.2.md` (or `0.10.0.md`, see the decision above) with
  every `@see` updated, and the first ticket rewrites its version-specific parts; `docker/kafka-0.9.0.1/` gains a
  sibling `docker/kafka-0.10.2.2/`, `docker-compose.yml` points at it, and `docs/CASCADE.md` gets its history row.

## Environment recipe (the same one that worked for 0.9.x)

1. **Docker**: `nohup dockerd >/tmp/dockerd.log 2>&1 &` if `docker info` fails. Build the broker from
   `docker/kafka-<version>/` — old Docker Hub images with v1 manifests cannot be pulled, but the Kafka tarball
   comes from `archive.apache.org`, which is reachable. Copy `docker/kafka-0.9.0.1/` and bump `KAFKA_VERSION`,
   `SCALA_VERSION` and `KAFKA_DIST`; the start script needs no change beyond the broker settings.
2. **The proxy-CA trick**: the sandbox intercepts TLS, so `curl` inside the image fails unless the proxy CA is
   trusted. `docker/kafka-0.9.0.1/ca/` is copied into `/usr/local/share/ca-certificates/extra/` and
   `update-ca-certificates` runs before the download; the directory is normally empty (see its `README.md`), and an
   agent that hits certificate errors during the build drops the proxy CA bundle
   (`/root/.ccr/ca-bundle.crt`) in there. Keep that mechanism in the new image.
3. **SSL listener**: the 0.9 image generates a JKS keystore/truststore from the checked-in `ssl/broker.crt` +
   `broker.key` at build time and binds `listeners=PLAINTEXT://0.0.0.0:9092,SSL://0.0.0.0:9093`. Carry it over —
   `KAFKA_SSL_BOOTSTRAP_SERVERS` (default `127.0.0.1:9093`) and `IntegrationTestCase::brokerCertificateFile()` are
   already wired for it. With SASL/PLAIN in scope, the new image also needs a JAAS file and a
   `SASL_PLAINTEXT`/`SASL_SSL` listener.
4. **Broker settings** that the 0.9 suite depends on: `auto.create.topics.enable=true`, `num.partitions=3`,
   `offsets.topic.replication.factor=1`, `offsets.topic.num.partitions=5`, `group.min.session.timeout.ms=1000`,
   `group.max.session.timeout.ms=60000`, `delete.topic.enable=true`. Add `message.format.version` /
   `log.message.format.version` fixtures for the 0.10 line: a topic configured with `message.format.version=0.9.0`
   is what proves the down-conversion path, and `message.timestamp.type=LogAppendTime` is what makes Produce v2
   return a real `log_append_time`.
5. **Dependencies**: `tools/dev/vendor-from-source.sh` once per session (Composer cannot download GitHub archives
   behind the proxy), then `cp -a vendor/` into every agent worktree; the script strips the packages' `.git`
   directories, and a tree with them fills the disk. Never run `composer update` there.
6. **Quotas**: `tests/Fixture/ClientQuota` sets and deletes a `producer_byte_rate`/`consumer_byte_rate` for the
   client id of a test with `kafka-configs.sh` inside the container (`docker exec`, container overridable with
   `KAFKA_CONTAINER`) and always removes it in a `finally` block. It works unchanged on 0.10.
7. **In-container tools**: `kafka-topics.sh --zookeeper localhost:2181`, `kafka-console-producer.sh`,
   `kafka-console-consumer.sh --new-consumer --bootstrap-server localhost:9092 --consumer.config <file>` (the 0.9/0.10
   console consumer needs the properties file for `group.id` and `partition.assignment.strategy`),
   `kafka-consumer-groups.sh --new-consumer`, `kafka-configs.sh`, and
   `kafka-run-class.sh kafka.tools.DumpLogSegments --files /tmp/kafka-logs/<topic>-0/00000000000000000000.log --print-data-log`,
   which is the fastest way to see what a message format really looks like on disk. `docker logs <container>` shows
   the api keys and versions the broker dropped.

## Ticket plan (waves of up to four Opus agents in isolated worktrees)

Wave 1 — foundation
- **T1 broker, surface and docs**: `docker/kafka-<version>/` (+ compose, SASL listener), the protocol document
  renamed and rewritten for the line, `ApiKeys` 17–20, error codes 32–44 from `main`, README/CHANGELOG headers, and
  the **ApiVersions api** itself (key 18) — it replaces the version probe of `0.9.x` and pins the api table of the
  document against the broker.
- **T2 message format v1**: magic byte 1 with the timestamp and the timestamp type, relative inner offsets in a
  compressed set, LZ4, and the down-conversion a broker does for a v0 consumer. This is the largest single piece of
  the line and it touches `Common\Record\*`, the producer and the consumer; give it a whole ticket and byte-exact
  vectors from `DumpLogSegments`.

Wave 2 — the versioned apis
- **T3 Metadata v1/v2**: nullable topic array, `controller_id`, broker `rack`, `is_internal`, `cluster_id`, plus
  `TYPE_BOOLEAN` in the engine and `Cluster`/`Node` carrying the rack and the controller.
- **T4 Produce v2 / Fetch v2 and v3**: `log_append_time`, the top-level `max_bytes` and the partition order it makes
  significant; `RecordMetadata` gains the append timestamp that 0.9 leaves `null`.
- **T5 Offsets v1**: offsets by timestamp, one offset per partition, and `KafkaConsumer::offsetsForTimes()`.
- **T6 OffsetFetch v2 + JoinGroup v1**: the nullable topic array with the top-level error code, `rebalance_timeout`
  and the `max.poll.interval.ms` half of it in the consumer.

Wave 3 — admin, security and the finish
- **T7 CreateTopics / DeleteTopics** (keys 19, 20) and the `AdminClient` methods, with the controller lookup
  (`NotController`, code 41) and `validate_only` of v1.
- **T8 SASL/PLAIN**: SaslHandshake (17) plus the token exchange on the socket, `security.protocol =
  SASL_PLAINTEXT`/`SASL_SSL`, `sasl.mechanism`, `sasl.jaas.*` equivalents — the first mechanism this client can
  really speak, because GSSAPI needs a binding PHP does not have.
- **T9 docs, compliance, examples, handoff for `0.11`/`main`**: the same closing ticket as this one.

Every ticket: byte-exact vectors from the real broker, integration tests with unique topic/group names, the whole
gate green before the PR, and a PR against the integration branch with "Closes #n".

## Pitfalls of the 0.9.x session (do not rediscover them)

* **JoinGroup blocks the connection** until the coordinator has finished the rebalance, so `request.timeout.ms`
  must exceed `session.timeout.ms` — and a test that needs **two members of one group needs two processes**
  (`tests/Fixture/consumer-group-member.php` + `ConsumerGroupMemberProcess`). A single-threaded PHP process cannot
  write the second join while it waits for the first answer.
* **`private` properties break versioned subclasses.** A `…V0` class that reuses the scheme of its parent needs the
  properties to be `protected`; `ProduceRequest` and `FetchRequest` had to be changed for that. Write new request
  classes with `protected readonly` promoted properties from the start.
* **Parallel agents collide on the compliance registry.** `ProtocolVectorTest::REPLAYED_APIS`, the preamble of the
  "Wire vectors" section and the api-key table were the only merge conflicts of the whole session, and every ticket
  that captured a vector hit them. The constant is gone since T9: a data provider is named after the file it reads
  (`offsetCommitVectors()` → `offset-commit.json`, `VectorFile::provideFor(__FUNCTION__)`) and
  `testEveryVectorFileIsReplayed()` derives the covered apis from the providers themselves, so a new api adds a
  file, a provider and a test method and touches nothing shared — keep it that way. The document has the same
  property per vector (`### <id>` blocks are conflict-free); its "Wire vectors" **preamble**, which enumerates
  every capture, and the api-key table still are not, so plan them into one ticket or accept the conflict.
* **A 0.9 broker drops an api it cannot parse and keeps the connection open — a 0.10 broker closes the socket.**
  `SocketServer.processCompletedReceives` @ 0.10.2.2 catches `InvalidRequestException`/`SchemaException` and closes
  the connection ("Closing socket for ... because of error"), where 0.9 only logged and went on. Tests written on
  `0.9.x` that expect silence for a wrong version (`ProtocolFramingTest`, `ApiVersionProbeTest`) therefore have to
  be rewritten for the new line, and the probe itself is replaced by an ApiVersions request.
* **Fresh topics answer 5/6 for a moment**, a broker without any topic answers Metadata with zero brokers, and the
  readiness probe of `IntegrationTestCase` is what deals with both. Several agents share one broker: unique
  `t<n>-…` topic and group names per test class, never delete a topic another agent created, never restart the
  broker from a subagent.
* **phpstan is a phar** (`php vendor/bin/phpstan`), php-cs-fixer runs over `src`, `tests` and `examples`, and
  `composer check` is the first three quarters of the gate; the integration suite is the last quarter and it is not
  optional.
* **Nested branch names** (`0.10.x/foo`) cannot exist next to the branch `0.10.x` — ticket branches are `t<n>-<slug>`.
* **GitHub `Closes #n` does not auto-close** an issue from a PR that targets a non-default branch: close the issues
  by hand after merging.
