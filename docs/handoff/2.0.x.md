# Handoff: the line above 1.x (Kafka 2.0)

State at handoff: the **1.x line is complete**. Everything a Kafka 1.1.1 broker speaks is implemented on the
`BinarySchema` engine and verified against a real broker — 1717 unit tests, 321 compliance tests replaying the
**314** wire vectors of the five lines (229 inherited, 85 captured on the 1.1.1 container) and 540 integration
tests against the 1.1.1 container over its four listeners, without a single skip. The grammar is written down in
[`docs/protocol/1.1.md`](../protocol/1.1.md), the machine-readable frames in
[`docs/protocol/vectors`](../protocol/vectors), the behaviour a client cannot read out of the grammar in that
document's "Broker quirks and observations" section, and the record of how the line was built — what was decided,
what the broker forced, what was left out — in [`docs/handoff/main.md`](main.md).

`main` is the branch the line above 1.x is built on, exactly as it was for 0.11 and for 1.x: the finished 1.x tree
is branched off as **`1.x`** at the commit that completes it, `main` carries on, and the cascade rules of
[`docs/CASCADE.md`](../CASCADE.md) apply unchanged. Like the 1.x line, this one starts from a finished,
schema-based implementation: there is nothing to drop and nothing to re-implement, every class of 1.1.1 is the
class the 2.0 version of the same api extends, and rule 4 of `CLAUDE.md` means "start from the 1.1 class and add
what the new release adds".

Read `CLAUDE.md` first (hard rules, toolchain, the Composer/phpstan sandbox workaround, Docker, the JIT caveat).

## First decision for the owner: which Kafka release the line speaks

Every line below speaks the **last** release of its Kafka line (0.8.2.2, 0.9.0.1, 0.10.2.2, 0.11.0.3, 1.1.1). On
that principle this line speaks **Kafka 2.0.1**, and everything below is written for it. Unlike the 1.x line, the
2.0 line raised the protocol **once**: 2.0.0 added everything, 2.0.1 is a bug-fix release and changed nothing on
the wire. The tag [`2.0.1`](https://github.com/apache/kafka/tree/2.0.1) exists in the Apache repository, so "@
2.0.1" is that tag, and `2.0.0` is only needed where a change has to be attributed to the feature release itself.

The alternative the owner may prefer is to skip to **2.1.x** or **2.2.x** and take KIP-320 (the leader epoch in
Fetch, ListOffsets, OffsetCommit and OffsetFetch) with it. That is a much larger raise: 2.0 is almost entirely a
*version bump without a schema change*, and doing it first gives the line a cheap, fully verified step and leaves
KIP-320 as a line of its own. This handoff assumes 2.0.1.

## What Kafka 2.0.1 adds over 1.1.1

**No new api key.** `ApiKeys.java` @ 2.0.1 still ends at `DELETE_GROUPS` (42), exactly as @ 1.1.1;
`ElectPreferredLeaders` (43) is Kafka 2.2. **No new primitive type, no new message format, no change to the
request header** — the record batch v2 (magic 2) is unchanged and `log.message.format.version` of a 2.0 broker is
`2.0-IV1` only to name the inter-broker protocol, not a new format.

What the release *does* is bump the version of nearly every api by one, and only four schemas really change:

| KIP | What changes on the wire |
|---|---|
| **KIP-219** (Improve quota communication) | The version of **every non-cluster-action api that can be throttled** is bumped by one, with a **byte-identical schema**. The new versions mean: the broker sends the response *first* and mutes the channel afterwards, so a throttled client must wait `throttle_time_ms` itself instead of discovering the delay as a late answer. This is 33 of the 36 version bumps below |
| **KIP-279** (log divergence after a fast leader failover) | **OffsetsForLeaderEpochResponse v1** gains a partition-level `leader_epoch` int32 between `partition_id` and `end_offset`. The *request* v1 is the v0 frame |
| **KIP-290** (prefixed ACLs) | **DescribeAcls v1**, **CreateAcls v1** and **DeleteAcls v1** gain a `resource_pattern_type` int8 (`LITERAL` 3, `PREFIXED` 4, and the filter values `ANY` 1 and `MATCH` 2) in every resource and every filter. The three apis stay out of this repository by the decision below |
| **KIP-283** (efficient down-conversion) | Nothing on the wire — but a broker down-converts **lazily and in chunks** now, and the topic option `message.downconversion.enable` / the broker option `log.message.downconversion.enable` can switch it off, in which case a Fetch below the format's version is answered **43** (`UNSUPPORTED_VERSION`) instead of a converted batch |

### Error codes

`Errors.java` @ 2.0.1 ends at **72**, one code above 1.1.1:

| Code | Name | Exception class | Retriable | Meaning |
|---|---|---|---|---|
| 72 | `LISTENER_NOT_FOUND` | `ListenerNotFoundException` | **yes** | The leader of a partition has no listener matching the one the Metadata request arrived on. `ListenerNotFoundException extends InvalidMetadataException` @ 2.0.1, so it is retriable exactly like 5 and 6 |

Everything else of `Errors.java` is unchanged, including the retriable set. `KafkaException::fromCode()` already
answers an unknown code with `UnknownErrorException`, so nothing breaks before the code is added; the ticket that
adds it also raises the range pinned by `KafkaExceptionTest`.

### Behaviour that changes without a wire change

* **KIP-219 is a client-side contract.** From the new version on, a broker that throttles a request answers
  **immediately** with the `throttle_time_ms` and mutes the channel for that long afterwards. A client that sends
  the new version must therefore honour the field itself; one that does not will simply see the next request stall.
  Kafka's own client waits `throttle_time_ms` before it sends again. `Client::dispatch()` of this repository
  currently reads the field and reports it (`RecordMetadata::$throttleTimeMs`, `FetchedPartition`), but waits for
  nothing — deciding what a PHP client should do here is the one real design question of this line.
* **KIP-186 raised `offsets.retention.minutes` from 1440 to 10080** (one day to seven). Any test that relies on an
  expired offset has to set the broker option down again, and the `Empty`-group cleanup of the 1.x line behaves
  differently on the default configuration.
* **KIP-266 changed the client defaults** `request.timeout.ms` (to 30 s) and added `default.api.timeout.ms`. Those
  are Java-client defaults, not protocol; this repository already documents its own.
* **KIP-283 made down-conversion lazy** and added `message.downconversion.enable`. With it off, a Fetch below the
  format's version is answered **43** (`UNSUPPORTED_VERSION`) instead of a converted batch — a new observable
  behaviour for the "What the broker converts, and when" section, and a way to *finally observe* a code the lower
  lines only documented.
* **KIP-176 removed `--new-consumer`** from the console tools. Every `kafka-console-consumer.sh --new-consumer`
  line in `CLAUDE.md`, in the protocol document and in the test fixtures has to lose that option on a 2.0 image —
  the option is an error there, not a no-op.
* **The ZooKeeper-backed offset storage is still served** (OffsetCommit/OffsetFetch v0), so
  `offsets.storage = zookeeper` keeps working; Kafka 2.0 only removed the *tools* that used it.

### What is deliberately not in this line

* **The ACL apis 29, 30 and 31 stay out** (decision 4 of epic #90, inherited from #70): they only do anything on a
  broker with an `authorizer.class.name`, and every wire vector of this repository is captured from a real broker.
  KIP-290 makes this cheaper to revisit, though — a container with `authorizer.class.name` and
  `super.users=User:ANONYMOUS` would let a ticket capture all three at v1 with both pattern types. If the owner
  wants ACLs, this is the line to do it on, as a ticket of its own with its own container.
* **KIP-320** (the leader epoch in Fetch, ListOffsets, OffsetCommit and OffsetFetch) is Kafka **2.1**.
* **Flexible versions and tagged fields** are Kafka 2.4.
* **SASL/OAUTHBEARER** (KIP-255) exists in the 2.0 sources, and it is *not* a protocol change: it is one more
  mechanism name in the SaslHandshake exchange, whose token is a bearer assertion. It could be added on this line
  or on any later one; it needs a broker configured with a JAAS login module for it, which the image does not have.
  SASL/SCRAM stays out for the same reason it does today — the multi-round exchange of RFC 5802 — and with it the
  *use* of a delegation token.

## The api-key table to expect

A 2.0.1 broker with `inter.broker.protocol.version=2.0-IV1` should answer ApiVersions with **43 keys, 0 to 42**,
the maxima of the table above. Capture the frame with the vector client id, store it as `apiversions.response.v0`
and `.v1` (the two answers are re-captured on every line) and make it the api-key table of the document. Note that
the *request* this line sends becomes **ApiVersions v2**, so a third pair of vectors is new here.

## Pitfalls of the 1.x session (do not rediscover them)

* **A stale container name makes tests skip, not fail.** The baseline of the inherited suite had seven hidden skips
  because `MessageFormatV1Test`, `RecordBatchV2Test` and the quota fixture still named `kafka-0-11-0-3`, and the
  SSL tests still pointed at the 0.11 certificate. Grep for the container and the image directory on day one, and
  demand **zero skips** from every gate.
* **`Protocol.java` is not the schema authority any more.** From Kafka 1.0 the schemas live in the request and
  response classes; a ticket that reads `Protocol.java` reads a file that no longer exists at these tags.
* **A 1.x/2.x broker closes the socket for a version above its table, for every api.** Only ApiVersions answers an
  unknown version (with 35). `docker logs <container>` is the answer to "why did my request never come back"; the
  message names the api, the connection, the listener and the principal.
* **`throttle_time_ms` is the LAST field of the four delegation-token answers (38-41)**, and SaslAuthenticate (36)
  has none; every other api of the 1.x line — DescribeLogDirs (35), AlterReplicaLogDirs (34), CreatePartitions
  (37) and DeleteGroups (42) included — carries it first, like every api KIP-124 touched. Reading a token answer's
  first int32 as a throttle time decodes its error code instead. Nothing in 2.0 changes this, and the v1 of the
  token apis inherits the trailing position.
* **A version bump with an identical schema still needs its own class and its own vector.** The 1.x line's
  `ProduceRequestV4` is `ProduceRequestV3` byte for byte and is still a class, because the api *version* in the
  header is what the broker branches on. Expect the same for all 33 KIP-219 bumps.
* **The broker is the authority on the error message, and the messages move between releases.** Kafka 1.0 rewrote
  three CreateTopics messages and the "unexpected broker id" message of DescribeConfigs (twice — the 1.1 one even
  quotes a Scala interpolation bug). Never assert on a message this repository has not measured on its own
  container.
* **A shared container is shared.** Unique topic, group and transactional-id prefixes per test class; never restart
  or recreate the broker from a subagent; never delete a topic the test did not create; a DescribeLogDirs with a
  `null` topic array answers every replica of *everybody's* tests (235 kB during the 1.x session).
* **Timestamps come from the clock**, never from a fixed date: the retention deletes a segment by its largest
  timestamp, so a vector captured with a 2020 timestamp disappears within minutes on a container whose clock says
  2026.
* **Merge seams between two tickets' vector dumps can lose a closing code fence** — `DocumentationSyncTest` catches
  it, so run the compliance suite after every merge of the integration branch, not only before the PR.
* **The tracing JIT of the sandbox's PHP 8.5 CLI miscompiles hot pure-PHP byte loops** (lz4, CRC-32C, varints).
  Always `php -d opcache.jit=0 vendor/bin/phpunit`; a failure that only appears with the JIT on is not a defect.
* **Agents subscribe to their own PR despite the brief.** Say it twice, and unsubscribe after reading a PR.
* **One flake was seen under load**: `AdminGroupApiTest::testAGroupStaysBehindEmptyWhenItsLastMemberLeaves` failed
  once while three full suites ran against the broker in the same second, and passed 3/3 on re-run. If it appears
  again on 2.0, make the helper retry rather than assume a broker change.

## Open questions for the owner

1. **KIP-219: does this client wait?** Sending Produce v6 or Fetch v8 is a promise to honour `throttle_time_ms`
   itself. The options are (a) send the new versions and sleep the throttle time before the next request to that
   broker, (b) send the new versions and only *report* the field, as today, accepting that a throttled client sees
   its next request stall, or (c) keep sending the 1.1 versions of the throttled apis, which a 2.0 broker still
   serves. (a) is what the Java client does and is what this handoff assumes; it is the only decision of the line
   that changes runtime behaviour rather than a version number.
2. **2.0.1 or straight to 2.1/2.2?** 2.0 is a cheap, fully verifiable step (four schema changes, one error code);
   2.1 brings KIP-320 and a real raise. Doing 2.0 first costs one session and gives the cascade another frozen
   line.
3. **ACLs at last?** KIP-290 is the moment the ACL apis change shape. A ticket with a second container
   (`authorizer.class.name=kafka.security.auth.SimpleAclAuthorizer`, `super.users=User:ANONYMOUS`) would let this
   repository capture 29, 30 and 31 at v1 from a real broker and finally observe the codes 53 and 65. It is the
   only ticket of the line that needs an image the rest of the suite does not use.
4. **SASL/OAUTHBEARER (KIP-255)?** It is a mechanism, not a protocol change, and it is implementable in pure PHP —
   unlike SCRAM. If it lands, the delegation-token limitation of the 1.x line stays exactly as it is (a token is a
   SCRAM credential), but `sasl.mechanism` gains its first alternative to PLAIN.
5. **When is `main` branched off as `1.x`?** The 0.11 and 1.x lines were both branched at the commit that completed
   them, so that `main` can carry the next line. The same is expected here; `docs/CASCADE.md` gets the row.
